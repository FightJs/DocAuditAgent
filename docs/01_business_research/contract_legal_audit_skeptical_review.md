# 合同／法务文档审核 Agent：反方审查与治理风险

## 1. 目标、边界与审查立场

本场景的目标是让 Agent 从合同及其相关材料中定位风险条款、缺失信息、版本差异和需升级的问题，并将可核查的证据交给业务、法务或合规人员处理。它应提高初筛覆盖率、缩短查找时间、促进条款标准化；不应自行作出具有约束力的法律判断、批准交易，或替代执业律师的意见。

反方审查的核心立场是：即使模型输出语言流畅、风险标签完整，也不能据此推定结论正确。合同风险依赖交易目的、主体资格、地域、监管规则、谈判历史和最新版本等上下文；系统必须把不确定性显式暴露，并保留人工否决和升级通道。

## 2. 审核对象与输入约束

审核对象包括：

- 合同正文及定义、附件、订单、SOW、数据处理协议和签署页；
- 历史版本、红线稿、已批准模板及条款库；
- 交易背景（金额、期限、主体、地域、产品、处理的数据类别）和适用政策；
- 作为检索依据的法律法规、监管指引和内部审批规则。

输入本身是首要风险源。扫描件 OCR 错字、未上传附件、错误地将草案视为定稿、条款库或法规过期、不同法域混用，均会使后续模型推理失去基础。系统应在审核前检查文件完整性、版本标识、可读性、来源与生效日期；无法确认时只能给出“材料不足”的升级结论，而不能补全事实。

## 3. 为什么需要 LangChain 支持人机交互流程

合同审核往往不是一次提示词问答，而是“解析—检索—比对—风险归类—人工决策—回写”的有状态工作流。LangChain 可用作流程编排层：将文档解析、条款检索、政策/法规检索、版本比较和结构化输出封装为受控工具；在高风险、低置信度、缺少证据或工具失败时暂停并请求人工输入；将审核人员的批准、否决、补充材料及理由作为下一步的明确状态。

但 LangChain 不应被视为可靠性的替代品。工具调用、记忆状态和检索链路会引入新的攻击面：提示注入可诱导工具越权，历史上下文可能污染当前结论，错误检索结果可能被模型包装成确定结论。因此每一次工具调用都需要最小权限、参数校验、结果来源标识和可审计追踪；“人工批准”也必须针对完整证据包，而非仅针对模型摘要。

## 4. 误报与漏报：失效机制和控制方法

| 风险类型 | 常见失效机制 | 业务影响 | 建议控制 |
| --- | --- | --- | --- |
| 误报 | 标准条款被脱离交易背景解释；规则阈值过严；OCR/分段丢失否定词 | 审核疲劳、业务延迟、用户绕过系统 | 分级展示置信度和影响；允许人工标注误报原因；用已裁决案例持续校准规则 |
| 漏报 | 未检索到附件或最新法规；模型未理解定义间引用；文本过长被截断 | 关键责任、赔偿、数据或合规风险未被升级 | 文件/附件完整性门禁；条款覆盖率检查；高风险条款必须人工复核 |
| 错误依据 | 过期、跨法域或无权威来源的检索材料被引用 | 错误法律建议被采纳 | 权威源白名单、版本与生效日期校验、引用来源和适用范围可见 |
| 错误版本 | 草案、红线稿、签署版关联错误 | 审核结论无法用于实际合同 | 文档指纹、版本谱系、签署版锁定和人工确认 |

对漏报的治理标准应严于误报：涉及责任限制、赔偿、自动续约、排他、知识产权、数据跨境、制裁/出口管制、个人信息或强制审批的条款，不应以模型“未发现风险”作为放行依据。应以预定义的关键条款清单验证覆盖，缺失或无法解析即升级。

## 5. 人工复核与责任边界

采用风险分级而非统一自动放行：低风险的格式/模板偏差可由业务确认；中风险的非标准商业条款应由条款负责人复核；高风险或法律不确定事项必须升级至法务/合规，并在必要时转外部律师。人工复核的输入至少包含原文定位、完整上下文、对比基准、检索依据、模型结论和不确定性说明。

职责应明确：系统所有者负责模型、规则、权限和运行监控；业务负责人对交易事实和商业取舍负责；法务/合规人员对其审阅后的专业意见与审批决定负责；最终签署授权人对合同签署负责。供应商或开发团队不得以“模型建议”模糊上述责任，也不得把自动化风险评分直接转化为法律意见或签署授权。

## 6. 证据溯源、权限与审计

每个风险项应可回溯至不可变的证据包：文档 ID 与哈希、页码/段落/字符范围、所用版本、提取时间、关联附件、检索查询、来源 URL 或内部规则版本、模型与提示词版本、工具调用结果、人工处置人及时间。若原文或依据无法定位，结论应标为不可核实，而非事实陈述。

权限设计遵循最小权限和职责分离：业务人员只能访问自己获授权的交易；法务可以查看其负责范围的全文及证据；系统服务账户仅具备完成特定工具调用所需权限；管理员权限与审核/签署权限分离。对个人信息、商业秘密和特权法律意见应执行数据分类、租户隔离、传输与存储加密、保留期限、导出限制和访问日志。禁止将未授权合同内容写入长期记忆、通用训练集或跨客户检索索引。

## 7. 上线前的治理门槛与未决风险

上线前应通过代表性合同集进行分法域、合同类型和风险类别的评估，并分别报告关键条款的召回率、误报率、证据可定位率、人工推翻率和升级时效；指标不能只看总体准确率。应建立抽检、红队测试、规则/模型变更审批、事故处置、回滚和定期再验证机制。

仍需由产品、法务、合规和安全共同确认的事项包括：允许覆盖的法域与合同类型、关键条款清单及强制升级阈值、权威法律来源、数据保留与跨境处理规则、人工 SLA，以及模型错误造成损失时的责任与通知机制。下一阶段应将这些决策固化为可测试的 API 契约、权限矩阵、审核状态机和验收用例。
