# LangChain HITL 文档审核流程架构规范 v1.0

## 1. 目的、范围与输入

本规范将既有业务模型与核心交互链路收敛为可由 LangGraph Human-in-the-loop（HITL）承接的文档审核流程约束，定义审核状态、中断点、恢复边界和人工决定的路由原则。它是后续系统架构、数据模型和 API 规范的输入，不定义实际接口、字段、存储实现、队列实现或后端代码。

本规范只使用以下既有项目输出作为业务依据：

- `docs/03_business_problem_modeling/document_audit_business_model.md`
- `docs/04_core_interaction_flows/interaction_flow_summary.md`
- `docs/06_system_architecture/frontend_backend_boundary_spec-v1.0.md`

适用范围为 MVP 的 NDA、标准采购或服务协议审核。Agent 形成带证据的候选风险项；有权限的人工审核者作出最终决定。Agent 完成、解析成功或未产生候选风险均不构成批准。

## 2. 调研依据与限制

### 2.1 LangChain MCP 的作用

**LangChain MCP 在本项目中的主要职责是获取 LangChain 官方最新的文档规范。** 它不是文档审核的运行时编排器，不替代 LangGraph 的 `interrupt`、checkpoint、恢复或业务审批控制。

本次调研优先尝试使用项目已配置的 `langchain-docs` 与 `langchain-reference` MCP。当前会话未提供对应的可调用 MCP 工具，资源发现结果为空；随后按项目配置显式重试，`codex mcp list` 显示两台服务为 enabled，但当前会话仍不能向其发起文档检索。因此，本文不把任何结论表述为本次 MCP 的实时查询结果。

以下仅列出可供后续联网复核的官方资料，本文据其已在项目初始化说明中归档的规范摘要，并结合上述项目输入形成受限架构设计：

| 官方主题 | 可核验链接 | 本文使用的规范要点 |
| --- | --- | --- |
| LangGraph Interrupts | https://docs.langchain.com/oss/python/langgraph/interrupts | `interrupt()` 暂停图执行并等待外部输入；以相同 `thread_id` 和 `Command(resume=...)` 恢复；中断节点会从节点开头重新执行。 |
| LangGraph Persistence | https://docs.langchain.com/oss/python/langgraph/persistence | checkpoint 用于保存可恢复的图状态；生产恢复依赖持久化状态而非浏览器内存。 |

## 3. 架构结论与职责分层

### 3.1 结论

文档审核应以“一个当前文档版本加一个固定审核基线所对应的一次审核运行”为 HITL 流程边界。该流程可以在满足人工介入条件时暂停；人工处置只通过受控恢复输入影响后续路由，不能直接覆盖原始文档、解析结果、Agent 候选结果或历史决定。

业务案件状态、审核运行状态和图执行的暂停/恢复状态必须分别维护和展示：

| 层次 | 表达对象 | 责任 |
| --- | --- | --- |
| 业务状态 | 案件和风险处置的 `parsing`、`agent_reviewing`、`human_reviewing`、`approved`、`changes_requested`、`rejected`、`delivered` 等语义 | 后端权威判定，前端按授权展示。 |
| 审核运行状态 | 某一文档版本与审核基线的准备、执行、完成、异常、待人工或已被新版本替代 | 后端编排，和业务状态保持可追溯关联。 |
| 图执行状态 | 可继续、暂停等待人工输入、已恢复、结束或不可恢复 | LangGraph 通过 checkpoint 保存；不向提交者误呈现为业务批准。 |

### 3.2 不可替代的后端控制

LangGraph 中断仅提供暂停与恢复机制。以下判断仍必须由后端在创建、路由和恢复时执行：操作者身份与审批权限、当前责任、案件/版本/运行是否仍有效、风险证据是否完整、审核基线是否匹配、状态转换是否合法、审计事件记录及面向不同角色的结果可见性。前端仅展示待办和证据包，并发起经人工明确确认的操作。

## 4. 审核运行主链路

```text
文档版本准入并完成解析
→ 固定审核基线并创建审核运行
→ Agent 形成候选风险和证据
→ 风险聚合与人工分流判定
→ [无需人工] 形成待交付结果
→ [需要人工] 暂停并进入人工复核
→ 人工恢复后按决定路由
→ 交付、补件重提、驳回或升级
```

### 4.1 进入审核流程的条件

只有当前文档版本已经通过材料准入、解析结果可用、质量信号满足既有继续条件，并且已绑定明确版本与适用范围的审核基线时，才可创建 Agent 审核运行。材料缺失、`rejected`、`parse_failed` 或解析质量不足时，不得把流程推进为 Agent 完成或批准；应进入补件、异常处置或人工队列。

### 4.2 Agent 输出后的固定分流

Agent 只形成候选风险、证据、置信度、建议动作和异常信号。出现以下任何条件时，审核运行必须进入人工复核路径，而不是自动交付或批准：

- 红线条款或高严重度风险；
- 低置信度、无原文定位、无适用依据或结论冲突；
- 解析质量问题、审核基线失效/冲突，或处理异常；
- 提交者提出异议、补件或新版本；
- 既有规范要求由人工承担的案件级同意、驳回或风险接受。

无人工介入条件仅表示可形成“待交付的审核结果”，不产生 `approved`。若业务将来引入低风险自动放行，必须先变更业务规则、权限、审计与用户可见性规范。

## 5. HITL 中断点与恢复路由

每个中断点都应产生与当前案件、文档版本、审核基线和审核运行一致的人工待办。发送给人工界面的内容必须是可显示、最小必要且 JSON 可序列化的摘要；原文、完整证据和历史由受控查询按权限提供，不应依赖客户端缓存作为恢复依据。

| 中断点 | 触发条件 | 人工获得的既有业务信息 | 允许的恢复结果 | 恢复后的业务路由 |
| --- | --- | --- | --- | --- |
| 解析/准入异常确认 | 材料缺失、解析失败或质量不足，且需要人工确定补件或人工准入 | 当前版本、材料/解析质量摘要、异常摘要、既有补件要求 | 要求补件、转人工处理、确认不可继续 | `changes_requested` 后等待新版本；或转人工队列；不可继续时保持失败/拒绝语义，不能写为通过。 |
| 风险分流确认 | 红线、高严重度、低置信度、无证据、规则冲突或异常结果 | 当前运行、风险项清单、原文定位与上下文、规则依据、置信度/质量信号、路由原因 | 接收人工待办、转交/升级、要求补件 | 进入 `human_reviewing` 或对应的责任队列；补件时结束当前运行的处置并等待新版本。 |
| 风险项人工复核 | 审核者需要逐项确认、修改或标记误报 | 单项风险及完整受权证据包、已有处置、当前版本/运行上下文 | 确认风险、编辑结论、标记误报、要求补件、转交/升级 | 写入关联人工决定并更新风险处置；转交保持人工路径；补件回到新版本链路。 |
| 案件级最终决定 | 所有必要风险项已处置，且有权限人员需作案件级决定 | 当前版本/运行、已处置风险、未处置项校验结果、授权范围、可交付结果摘要 | 同意、驳回、要求补件、转交/升级 | 仅经授权的同意进入 `approved`；驳回进入 `rejected`；补件进入 `changes_requested`；转交/升级返回人工队列。 |

“接收待办”可以是进入人工队列后的分配动作，但不能单独视作最终业务决定。恢复输入必须代表审核者已明确提交的动作和理由；后端在恢复前仍须重新校验授权、当前责任、版本、运行、处置完整性和状态。

## 6. 持久化、恢复与版本边界

### 6.1 持久化要求

HITL 流程必须使用可持久化的 checkpoint 保存执行状态，并用稳定的 `thread_id` 标识同一审核运行的恢复上下文。该标识应与当前案件、文档版本、审核基线和审核运行保持可追溯关联；具体标识格式、存储产品及字段设计留待数据模型和后端实现阶段定义。

checkpoint 用于恢复图执行，不替代业务审计。案件状态、人工决定、版本关系和关键状态变更仍需作为后端权威业务记录及不可变审计事件保留。恢复动作及其操作者、时间、理由、结果和关联上下文同样必须可审计。

### 6.2 恢复前置条件

只有在下列条件全部成立时，才可通过同一 `thread_id` 恢复已暂停的流程：

1. 当前操作者具备相应案件访问权、待办责任和动作权限。
2. 暂停所绑定的文档版本、审核基线和审核运行仍是当前有效处理对象。
3. 暂停原因、证据包和待处理事项仍存在，且当前状态允许该动作。
4. 恢复值是结构化、JSON 可序列化且已通过业务校验的人工决定，不携带未获授权的原始内容或客户端推断结论。

恢复时应向 LangGraph 传入同一 `thread_id` 与对应的恢复命令。若恢复被拒绝，前端应重新获取后端权威状态和待办，不得将本地的旧表单提交展示为成功。

### 6.3 不可恢复与重审边界

下列情形不得恢复旧的暂停流程：

- 提交者补件、修改原文或增加会影响审核范围的材料；
- 审核基线、条款库、红线规则或适用范围发生变化；
- 当前运行已交付、归档、取消，或已由新的文档版本/审核运行替代；
- 待办责任、权限或状态已改变，导致原操作者无权继续；
- 暂停上下文或关键证据不再可用，无法安全确认决定依据。

上述情况应保留旧版本、旧运行和旧 checkpoint 对应的历史为只读，并创建或路由到新的文档版本/审核运行。不得用新材料或新基线恢复旧 `thread_id`，也不得覆盖旧决定使其看起来属于新版本。

## 7. 中断节点的运行约束

根据 LangGraph 官方 Interrupts 规范，中断后的恢复会从中断节点开头重新执行。后续实现必须遵守以下约束：

- 中断前会产生外部副作用的步骤必须幂等，或移至中断之后；不得因恢复重复创建人工待办、重复发送通知或重复写入决定。
- 不以宽泛异常捕获吞掉中断信号；中断是正常的暂停控制流。
- 同一节点内如存在多个中断，调用顺序必须稳定；变更中断数量或顺序应视为影响已有暂停流程的兼容性变更。
- 不在单个节点中使用无限循环反复中断；校验和重试通过状态与条件路由表达，避免恢复次数与中断顺序失配。
- 中断 payload 和恢复值保持 JSON 可序列化、最小化，并符合角色可见性；不得写入真实密钥、服务端内部提示或未经授权的其他案件信息。

## 8. 状态映射与展示约束

| 业务情形 | 后端权威状态/处置 | HITL 语义 | 前端允许的表达 |
| --- | --- | --- | --- |
| 解析或 Agent 正在执行 | `parsing` 或 `agent_reviewing` | 未暂停时持续处理 | 处理中，不承诺结果或完成时间。 |
| 解析失败或质量不足 | `parse_failed`、补件或人工分流 | 可在需要人工决定时暂停 | 失败/待补件/待人工处理，绝不显示为无风险或已通过。 |
| Agent 发现需复核事项 | `triaged` 后进入 `human_reviewing` | 在待人工输入处暂停 | 待人工复核，展示路由原因和获授权证据。 |
| 审核者正在处理 | `human_reviewing` | 暂停等待有效恢复输入 | 待当前责任人处理，不能由前端本地改为完成。 |
| 具备批准权限的人工同意 | `approved` | 恢复后结束或进入交付节点 | 已同意，仍标明当前版本/运行。 |
| 驳回或要求补件 | `rejected` 或 `changes_requested` | 结束当前处置；补件后新建处理上下文 | 已驳回或待补件，不展示为审核通过。 |
| 版本/基线变化 | 新版本或新运行 | 旧流程不可恢复 | 新版本处理中；旧版本只读历史。 |

## 9. 关键决策、风险与下一阶段输入

### 9.1 关键决策

1. HITL 的恢复边界以“文档版本 + 审核基线 + 审核运行”为准，不以单一案件或前端页面会话为准。
2. `approved` 始终是经授权人工的案件级决定；Agent 的候选输出只用于证据化分流和辅助判断。
3. 解析质量异常、风险证据缺失/冲突及高影响风险均强制进入人工路径。
4. checkpoint 用于流程恢复，业务状态和审计事件用于业务权威性与可追溯性，两者不得相互替代。

### 9.2 待解决风险

| 风险 | 对后续设计的约束 |
| --- | --- |
| 当前会话无法实时调用 LangChain MCP | API/SDK 实施前必须用官方 MCP 重新核验对应版本的 interrupt、checkpoint 和恢复语义。 |
| 恢复节点可从节点开头重执行 | 需要在后端设计中明确幂等边界、待办去重和通知去重。 |
| 人工处置与版本更新可能并发 | API 和数据模型阶段需定义乐观并发校验、过期待办的拒绝与重新加载行为。 |
| 证据和审批内容具有法务敏感性 | 权限、可见性、审计保留和 payload 最小化必须在系统架构与数据模型阶段具体化。 |

### 9.3 下一阶段交付物

| 后续阶段 | 必须承接的输入 |
| --- | --- |
| 系统架构设计 | 图编排与业务服务边界、持久化 checkpoint、异步任务、权限及审计的职责分离。 |
| 数据模型设计 | 案件/版本/基线/运行与图线程、人工待办、人工决定、审计事件的关联和只读历史规则。 |
| API 规范 | 状态查询、待办获取、证据读取、人工动作提交、过期恢复拒绝和新版本重审的业务契约。 |
| 后端实现计划 | 中断前副作用幂等、恢复校验、并发控制、异常路由和官方 SDK 版本复核。 |

## 10. 阶段结论

本规范在既有文档审核业务模型和交互链路基础上，明确了 LangGraph HITL 只负责暂停与恢复、后端负责业务裁决的架构边界。系统在任何需要专业判断、证据不足或版本失效的节点均保留人工控制；恢复仅适用于同一有效版本、基线和审核运行，历史永不被新结论覆盖。
