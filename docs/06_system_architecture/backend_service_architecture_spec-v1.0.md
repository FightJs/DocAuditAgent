# DocAuditAgent 后端服务架构规范 v1.0

## 1. 目的、依据与边界

本规范从后端服务视角收敛文档审核 MVP 的文件接收、版本化解析、审核任务状态、审核结构查询、人工交接和审计职责，为后续数据模型与 API 规范提供业务边界。

本规范仅依据以下既有文档：

- `docs/03_business_problem_modeling/document_audit_business_model.md`
- `docs/04_core_interaction_flows/interaction_flow_summary.md`
- `docs/06_system_architecture/frontend_design_spec-v1.0.md`
- `docs/06_system_architecture/frontend_backend_boundary_spec-v1.0.md`

后端是案件、文档版本、解析结果、审核基线、审核运行、风险项、证据、人工决定和审计事件的权威维护方。前端仅在用户明确操作时发起请求，并展示后端按授权范围返回的事实与可执行动作。

本规范不定义服务框架、数据库、对象存储、队列、解析器、模型、鉴权技术、API 路径或字段，也不构建任何后端代码。

## 2. 后端服务职责总览

| 服务职责域 | 后端必须维护的业务能力 | 不属于本职责域的事项 |
| --- | --- | --- |
| 案件与授权控制 | 创建审核案件，校验主体、角色、案件访问范围与审批权限，按授权过滤业务数据和可执行动作。 | 以页面可见性或客户端声明作为授权依据。 |
| 文件接收与材料准入 | 受控接收文件，确认材料角色、版本关系、完整性、实际类型、策略限制、安全性与可打开性。 | 信任浏览器侧类型、大小、可读性或上传成功提示。 |
| 文档版本与解析管理 | 为每次有效提交创建文档版本，编排解析任务，维护标准化解析结果、原文定位锚点和质量信号。 | 覆盖历史原件、解析结果或将质量不足视为正常可审核。 |
| 审核准备与运行管理 | 固定当前文档版本与审核基线，创建审核运行，维护运行状态、候选风险、证据及路由结果。 | 将 Agent 输出或空风险项解释为批准。 |
| 人工审核交接与决定执法 | 形成可复核证据包，路由人工待办，校验责任、权限、当前版本和运行，并保存决定。 | 让客户端直接写入终态，或允许无权主体批准案件。 |
| 审核结构查询与交付 | 面向已授权角色返回案件、版本、运行、风险、证据、待办、决定、时间线及交付结果。 | 返回其他案件、未授权内部轨迹或未交付的受限信息。 |
| 状态编排与审计 | 校验状态转换、幂等和并发条件；对关键事实和决定追加不可变审计事件。 | 由通知、前端缓存或重试结果替代权威状态。 |

## 3. 业务对象与权威归属

后端以审核案件为生命周期容器，维护下列对象及其关联。该表表达业务归属，不定义存储模型或字段。

| 业务对象 | 后端维护的权威事实 | 关键关联与不可变要求 |
| --- | --- | --- |
| 审核案件 | 审核范围、当前业务状态、当前责任、可见性与交付/归档语义。 | 包含一个或多个文档版本和审核运行；状态历史可追溯。 |
| 文档版本 | 当前批次的合同正文、附件、材料角色、原件身份、提交说明与版本关系。 | 属于一个案件；新上传、替换、补件或文本修改创建新版本，旧版本只读。 |
| 解析结果 | 标准化文本与结构、原文定位锚点、解析/OCR 来源和质量信号。 | 对应一个文档版本；不能被用作其他版本的证据。 |
| 审核基线 | 模板、条款库、红线规则、适用范围及其版本化引用。 | 被审核运行固定引用；变更后不得静默影响历史运行。 |
| 审核运行 | 特定文档版本与审核基线组合下的执行状态、异常、候选结果和分流结果。 | 属于案件；新文档或新基线触发新运行，历史运行只读。 |
| 风险项与证据 | 风险类别、严重度、置信度、候选建议、处置状态及对应原文、上下文与依据。 | 风险项属于审核运行；证据必须关联当前文档版本和基线。 |
| 人工待办与决定 | 当前责任人/队列、路由原因、人工确认、编辑、误报、补件、驳回、转交或升级。 | 决定关联案件或风险项、操作者、理由、时间、当前版本和运行；以追加方式保存。 |
| 审计事件 | 关键状态、规则选择、版本关系、责任变化、人工动作与交付事实。 | 关联对应案件及必要的版本/运行/决定；不得因展示限制删除。 |

## 4. 文件上传、准入与解析任务

### 4.1 文件接收边界

后端只在已确认的案件和授权范围内接收材料。每份文件须作为合同正文或支持附件进入当前提交批次，且不明角色的文件不能进入审核输入。服务端在文件到达受控接收区后完成最终准入判断；在必要校验完成前，文件不可供解析、审核或其他用户使用。

服务端准入至少覆盖以下业务判断：

| 判断类别 | 后端判定结果 | 后续业务处理 |
| --- | --- | --- |
| 接收完整性与重复提交 | 当前请求是否完整，案件、版本与幂等语义是否一致。 | 固化接收事实，或安全重试/返回冲突；不生成相互覆盖的版本。 |
| 文件真实性与策略范围 | 实际文件类型、大小、页数、数量及声明内容是否符合允许范围。 | 允许继续，或拒绝/要求调整材料。 |
| 安全性与可打开性 | 文件是否可被安全处理、是否损坏或受保护到无法处理。 | 可处理文件进入解析准备；异常文件隔离或拒绝，不进入自动审核。 |
| 材料完整性与范围一致性 | 合同正文、附件、版本说明和审核范围是否满足当前准入要求。 | 创建可处理版本，或建立补件待办/拒绝当前版本。 |

上传完成只能表示后端已接收材料，不表示解析完成、Agent 审核开始、风险为空或案件已批准。

### 4.2 版本化与解析任务创建

当当前版本的必要材料已通过准入，且不存在未解决的安全隔离、材料缺失或策略冲突时，后端为该文档版本创建独立解析任务。该任务必须与案件、文档版本、原件身份、材料角色、解析能力版本、创建时间和幂等语义保持关联。

解析为异步业务任务。后端创建任务后即可向前端返回当前状态，后续由任务状态更新与授权查询呈现进度；上传请求不得承担长文档解析或审核完成的等待责任。

解析结果须为后续审核和人工复核提供标准化文本、页/段落/表格/坐标等可定位结构、必要的页图引用及质量信号。低质量、无可用输出或失败必须显式表达，不能被解释为“未发现风险”。

### 4.3 解析任务的准入结果

| 结果 | 后端业务含义 | 对后续链路的约束 |
| --- | --- | --- |
| `accepted` | 材料已通过接收和准入，可进入解析编排。 | 不代表审核准备完成。 |
| `parsing` | 当前版本正在生成解析表示与质量信号。 | 不可使用未完成输出形成审核结论。 |
| `ready` | 已具备满足门槛的可定位解析结果。 | 可进入审核基线匹配和审核运行创建。 |
| `materials_requested` / `changes_requested` | 材料、说明、范围或质量需要补充。 | 不创建可用于审核的当前结论；补交形成新版本。 |
| `manual_intake_review` | 文件可处理但质量或准入冲突需要人工判断。 | 不得静默继续自动审核。 |
| `rejected` / `parse_failed` | 当前版本不能进入或不能完成可信解析。 | 不得显示为已通过、无风险或可交付。 |

## 5. 任务状态管理与审核编排

### 5.1 状态管理原则

1. 后端是状态转换的唯一裁决方。客户端操作、后台任务、重试和通知只能提交事实或请求，不可直接宣告业务终态。
2. 案件总体状态、文档版本状态、解析结果状态、审核运行状态和风险项处置状态应分别维护，并通过关联表达整体进度，避免用一个状态掩盖失败或人工待办。
3. 每次转换必须校验当前版本、审核基线、责任主体、权限和并发条件，并记录原状态、目标状态、原因、主体及时间。
4. 解析或审核失败、材料拒绝、质量不足和等待人工处理均不等于批准或无风险。
5. 文档材料、审核范围或审核基线发生变化时，后端创建新文档版本或新审核运行；旧版本、旧运行、候选结果与人工决定只读保留。

### 5.2 案件级主状态编排

```text
创建案件 → 上传与准入 → 解析与标准化 → 审核准备
→ Agent 审核 → 分流 → 人工复核/补件 → 交付 → 归档
```

后端对案件级状态应遵循以下业务语义：

| 状态 | 进入条件 | 后端必须保证的含义 |
| --- | --- | --- |
| `created` / `uploading` | 已创建案件或正在受控接收材料。 | 尚未形成可审核输入。 |
| `accepted` / `parsing` / `ready` | 准入已通过、解析执行中或解析结果可用于下一阶段。 | 仅表达材料与解析进度，不表达审核结论。 |
| `agent_reviewing` | 已固定当前版本和基线并启动审核运行。 | Agent 仅生成候选风险和不确定性信息。 |
| `agent_completed` / `triaged` | 候选结果已形成，正在或已按规则分流。 | 不代表人工批准；人工触发条件仍必须生效。 |
| `human_reviewing` | 风险、质量、规则或异议满足人工路由条件。 | 当前责任由人工队列或审核者承担。 |
| `changes_requested` / `resubmitted` | 人工或准入环节要求补件，或提交者已提交更新材料。 | 新材料进入新版本处理，历史记录不被覆盖。 |
| `approved` / `delivered` | 具备权限的人员已基于当前有效版本、运行和证据作出决定，且交付检查完成。 | `approved` 是人工决定；自动化处理成功不能替代此状态。 |
| `rejected` | 当前案件或当前文本未获人工批准，或当前版本被准入拒绝。 | 必须按对象和原因区分，并且不可被呈现为通过。 |
| `parse_failed` / `agent_failed` | 解析或审核运行未得到可用输出且不能继续自动处理。 | 提供可行动的补件、重试或人工处理路径。 |
| `archived` | 已完成交付或按保留策略结束处理。 | 保持授权范围内的只读历史。 |

### 5.3 审核运行与人工分流

当文档版本处于 `ready`，后端必须先为运行引用明确版本和适用范围的审核基线，再启动 Agent 审核。Agent 产生的每个候选风险须保留风险类别、严重度、置信度、建议动作、原文定位、上下文和关联依据。

后端基于既有业务规则将红线或高严重度、低置信度、无可定位证据、解析质量异常、规则冲突和提交者异议路由至人工队列。该分流不等同于 Agent 对案件的最终判断，也不得由前端根据风险数量自行决定。

进入人工队列时，后端应使案件关联当前文档版本、审核基线、审核运行、风险项及证据、质量/失败摘要、路由原因、既有决定和状态时间线，形成完整的人工复核上下文。

### 5.4 异常、重试与并发

可恢复的解析或审核异常可以进入有界重试；后端需保持同一任务及其尝试之间的关联，避免重复请求产生相互覆盖的结果。重试耗尽、输出无效、质量不满足门槛或规则无法适用时，后端应转为失败、补件或人工处理路径。

在补件、重提、基线变更、转交或人工决定提交时，后端必须重新确认当前版本、运行、责任和权限。若发现上下文已被新版本或新运行替代，拒绝将旧上下文的操作写为当前结论，并返回可行动的当前状态。

## 6. 审核结构查询与结果交付

### 6.1 查询边界

后端按角色、案件范围、当前责任和交付可见性提供审核结构查询。返回内容必须使用当前版本和当前审核运行作为明确上下文，避免将历史结果误作最新结论。

| 查询主题 | 后端提供的业务结构 | 授权与一致性约束 |
| --- | --- | --- |
| 案件概览与队列 | 案件标识、合同类型、审核范围、当前状态、当前责任、最近更新时间、待办摘要及历史入口。 | 仅返回有案件访问权的记录；状态以服务端权威时间线为准。 |
| 材料与版本 | 当前正文和附件、材料角色、版本说明、版本关系、历史只读标识及准入/解析概况。 | 当前与历史版本不可混用；原件与派生内容均受访问控制。 |
| 处理状态与异常 | 当前阶段、质量信号、失败或重试摘要、路由原因和可执行下一步。 | 向提交者隐藏内部安全规则、模型轨迹和无关运行细节。 |
| 审核运行与基线 | 当前运行、关联基线及版本、运行状态、适用范围与替代关系。 | 只能将结果与其固定的版本和基线一起展示。 |
| 风险项与证据 | 风险类别、严重度、置信度、处置状态、原文定位、上下文、依据与建议动作。 | 提交者仅获得授权交付内容；审核者获得完成处置所需证据包。 |
| 人工待办与决定 | 当前责任、路由/升级信息、已保存决定、理由、关联风险项、时间和历史。 | 权限、任务责任和终态限制由服务端校验。 |
| 交付与审计时间线 | 经可见性过滤的结论、限制条件、下一步与状态/决定事件摘要。 | 未交付内部意见、其他主体信息和受限策略不得外泄。 |

### 6.2 查询结果的表达规则

- 后端必须使 `approved`、`delivered`、`rejected`、`changes_requested`、`parse_failed` 与 `agent_failed` 等状态在业务语义上可区分；不得以“完成”一词掩盖不同结果。
- 面向提交者的交付只包含已授权、已完成处置且可对外展示的信息；内部模型推理、安全检测细节和未核实候选内容不属于默认交付。
- 风险项、证据、人工决定和交付结果必须能追溯到案件、当前或历史文档版本、审核运行和审核基线。
- 对无原文定位或适用依据的候选风险，查询结果应明确其待人工确认属性；不得作为放行依据。
- 历史版本、历史运行和既有决定可以按权限查询，但以只读事实提供，不能借查询或前端编辑覆盖。

## 7. 人工决定与审计边界

后端接收人工操作请求时，必须校验操作者权限、当前责任、案件状态、当前文档版本、审核运行有效性、证据完整性及并发状态。提交被接受后，后端保存新的人工决定并更新允许的案件或风险项状态；原始文件、原始证据、Agent 候选结果、基线引用及历史决定均不被改写。

| 人工操作 | 后端必须核验 | 可产生的业务后果 |
| --- | --- | --- |
| 接收待办 | 队列权限、案件访问权和当前可分配性。 | 更新当前责任或明确拒绝分配。 |
| 确认、编辑或标记误报 | 风险项可见性、当前版本/运行、复核权限及理由/依据。 | 追加风险项处置决定；案件保持人工处理中，直至满足终态条件。 |
| 要求补件 | 当前责任、缺失项说明、关联范围和权限。 | 建立补件待办，案件转 `changes_requested`；重提后创建新版本。 |
| 同意 | 当前有效版本、运行、必要风险项处置、证据完整性、授权条件及决定理由。 | 记录人工批准并转 `approved`；符合交付条件后才可 `delivered`。 |
| 驳回 | 案件级权限、当前上下文、依据和理由。 | 追加驳回决定，案件转 `rejected`。 |
| 转交或升级 | 转出/接收权限、目标队列或角色、责任变更原因。 | 更新责任或队列，案件保持 `human_reviewing`。 |

对关键业务事实，后端追加不可变审计事件。事件至少能够还原操作主体及其授权上下文、发生时间、目标对象、原状态和目标状态、当前文档版本、审核运行、基线引用、相关证据/理由和责任变更。审计记录可按权限过滤展示，但不得被删除或由客户端重写。

## 8. 前后端交接与后续规范输入

前端负责组织用户输入、展示服务端返回的当前状态与已授权结构，并发起明确的创建、上传、补件、查询、待办接收和人工决定操作。后端负责上述操作的最终校验、状态裁决、版本化、异步编排、查询过滤和审计留痕。

后续 API 规范应以本文件为业务输入，覆盖下列交接，而不暴露后端内部实现：

| 交接阶段 | 应保持关联的业务信息 |
| --- | --- |
| 上传与准入 → 解析 | 案件、文档版本、材料角色、原件身份、准入结论、解析任务、质量信号与审计引用。 |
| 解析与审核准备 → Agent 审核 | 当前版本、可定位解析结果、审核范围、审核基线及版本、审核运行与状态。 |
| Agent 审核 → 人工复核 | 审核运行、风险项、证据、严重度、置信度、解析质量、失败摘要、路由原因和历史决定。 |
| 人工决定 → 交付或重提 | 人工决定及理由、授权责任人、关联版本/运行/证据/规则、可见性过滤结果与审计记录。 |

后续数据模型设计应以对象归属、版本不可变、运行固定输入、决定追加和审计关联为基础；后续 API 设计应明确各查询与操作的授权、当前版本/运行校验、状态结果和失败语义。任何自动放行、额外合同类型、外部系统集成或新的状态语义，均须先更新业务规则与 Plan。

## 9. 验收边界

本规范在后续实现阶段应至少验证以下业务结果：

- 不完整、不安全、不可读或不适用的材料不能进入 Agent 审核。
- 每次提交、补件或文本修改均能形成可追溯的新版本，且不会覆盖历史结果。
- 解析和审核任务的成功、失败、重试、质量异常及人工分流能以不同状态表达。
- 审核结构查询能将风险、证据、决定和交付关联至正确的版本、运行和基线，并按授权范围过滤。
- 高严重度、低置信度、无证据、质量异常、规则冲突与异议均不能绕过人工处理。
- `approved` 与 `delivered` 只能由满足当前版本、证据和授权条件的人工决定形成。
- 关键状态变化、版本关系、责任变化和人工操作均能还原为审计事实。
