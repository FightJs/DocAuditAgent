# 文档审核中间状态与异常处理规范

## 1. 目标、范围与非目标

本规范定义 DocAuditAgent 在文档已提交、尚未形成最终交付结论期间的状态语义和交互规则。重点覆盖解析中、Agent 审核中、解析或审核失败、重试、补件/重提、状态可见性，以及自动化流程向人工审核的交接。

目标是让提交者知道案件正在发生什么、下一步由谁完成；让审核者拿到足以接手的证据和失败上下文；并保证失败、降级或等待处理不被误解为审核通过。

本规范不定义 API、数据表、任务队列、轮询/推送实现、重试次数、服务等级目标或具体通知渠道。它也不新增自动放行规则，且不将 Agent 输出解释为法律意见或最终批准。

## 2. 设计输入、假设与边界

### 2.1 既有业务输入

本规范继承 `docs/03_business_problem_modeling/document_audit_business_model.md` 的业务约束：审核案件是生命周期主体；文档版本和审核基线共同决定一次审核运行；风险项必须有可复核证据；高风险、不确定、质量异常或规则冲突事项必须进入人工队列；人工决定是最终控制点；历史版本和运行结果只读保留。

同时继承端到端流程调研中“解析质量参与路由”“有界重试”“失败不能视为无风险”“仅向有权主体展示结果和内部信息”的建议。

### 2.2 工作假设

- MVP 聚焦规则成熟、边界清晰的合同类型，如 NDA、标准采购或服务协议。
- 一个案件可包含多个文档版本；一次文档修改、补件合并后重新提交或审核基线变更，均创建新的文档版本或审核运行。
- Agent 仅形成候选风险项。除非未来另行制定、授权并审计低风险自动放行规则，`approved` 仅由有权限的人工审核者作出。
- 状态时间线为案件的权威历史；界面展示可以是面向角色的简化说明，但不得改变状态的业务含义。

### 2.3 边界

“处理中”说明系统正在尝试完成既定步骤，不代表对文档内容的任何正面判断；“失败”说明该步骤未获得可用输出，也不代表未发现风险。文档中只展示与接收者职责和权限有关的信息，内部模型轨迹、基础设施细节、安全检测策略和其他案件信息不对提交者开放。

## 3. 状态对象与状态语义

### 3.1 状态归属

| 对象 | 承担的状态 | 作用 |
| --- | --- | --- |
| 审核案件 | `created`、`uploading`、`accepted`、`rejected`、`parsing`、`parse_failed`、`ready`、`agent_reviewing`、`agent_completed`、`agent_failed`、`triaged`、`human_reviewing`、`approved`、`changes_requested`、`delivered`、`resubmitted`、`archived` | 面向业务的总体进度和当前责任归属。 |
| 文档版本 | 已接收、解析中、可用、解析不可用、已被后续版本替代 | 标识原文件及其派生解析结果是否可用于某次运行。 |
| 解析结果 | 处理中、合格、质量不足、失败 | 提供文本、结构、页码/坐标定位和质量信号；不作合规判断。 |
| 审核运行 | 准备中、审核中、已产出候选结果、失败、已被替代 | 固化特定文档版本与审核基线下的执行状态。 |
| 人工待办 | 待接手、处理中、已决定、已退回补件、已升级 | 表示必须由有权限人员采取行动的工作项，而非系统运行状态的替代。 |
| 审计事件 | 只追加，无可逆状态 | 记录状态变化、触发原因、操作者/系统主体、时间、关联版本和运行。 |

### 3.2 中间状态的用户语义

| 案件状态 | 系统语义 | 提交者看到的语义 | 当前责任主体 | 允许的下一步 |
| --- | --- | --- | --- | --- |
| `accepted` | 文件已通过准入，等待或准备解析。 | “材料已接收，正在准备读取。” | 系统 | 开始解析；必要时发起补件。 |
| `parsing` | 正在提取文本、布局和质量信号，扫描件可能包含 OCR。 | “正在读取文档；尚未开始审核。” | 解析服务 | 进入 `ready`，或转 `parse_failed` / 补件。 |
| `ready` | 解析结果可用，且已匹配可用审核基线。 | “材料已准备完成，等待审核开始。” | 审核编排器 | 开始审核运行。 |
| `agent_reviewing` | 正在以固定的文档版本和基线生成候选风险项。 | “正在审核；结果尚未完成。” | Agent/编排器 | 进入 `agent_completed`，或转 `agent_failed`。 |
| `agent_completed` | 已得到候选结果，尚未完成分流或人工决定。 | “初步审核完成，正在确认后续处理。” | 风险分流服务 | 进入 `triaged` 或触发人工接手。 |
| `triaged` | 已根据规则、严重度、置信度和质量信号确定路由。 | “审核结果正在由相应人员处理。”或展示获授权的下一步。 | 系统/人工队列 | 转人工复核、补件或按已授权流程交付。 |
| `human_reviewing` | 有权限的审核者已接手案件或风险项。 | “正在由审核人员复核。” | 法务/合规审核者 | 批准、要求修改/补件、拒绝或升级专家。 |
| `changes_requested` | 当前版本不能继续交付，需要提交者补充材料或修改后重提。 | “需要补充或修改材料后重新提交。” | 提交者 | 补件或创建新版本重提。 |
| `resubmitted` | 新材料或新版本已提交，历史运行保留只读。 | “已收到更新材料，正在重新处理。” | 系统 | 回到 `accepted` / `parsing` 并创建新运行。 |

`approved` 和 `delivered` 不是中间状态：前者是有权限人工作出的业务决定，后者是按可见性策略向提交者交付已完成处置结果。`parse_failed`、`agent_failed`、`rejected` 和 `changes_requested` 均不得以绿色成功样式、完成进度或“未发现问题”文案展示。

## 4. 状态可见性与用户信息

### 4.1 提交者

提交者应始终能看到当前案件的面向行动状态、最近更新时间、当前处理主体类别和自己可以采取的下一步。处理中仅显示阶段性描述，例如“正在读取”“正在审核”“正在人工复核”，不显示模型推理、内部重试策略、他人身份、其他案件或未授权风险详情。

当需要提交者行动时，界面必须把行动置于状态说明之前：需要哪些材料、对应哪个文档版本/附件、可接受的格式或修改要求、提交截止时间（如业务规则定义）以及重提将产生新版本。无法安全说明底层原因时，应提供可操作的替代说明，例如“文件无法读取，请上传未加密的清晰副本”，而不是暴露安全检测细节。

### 4.2 法务/合规审核者

审核者可见案件阶段、文档版本、解析质量、审核基线版本、失败/重试摘要、风险项、原文定位、分流原因、历史人工决定和待处理责任。界面应明确区分“系统未完成”“系统失败”“候选结果已生成”和“人工已决定”，避免审核者将空结果当作低风险结论。

### 4.3 管理员与策略负责人

管理员/运营负责人可查看队列积压、失败类别、重试和升级统计、权限与审计事件；策略负责人可查看与其规则版本相关的失配、冲突和人工改判反馈。两者均不得借此代替案件审核者作出具体法务决定。原文和证据访问仍受案件授权控制。

## 5. 异常分支与处理规则

| 异常 | 识别信号 | 案件处理与展示 | 不允许的处理 |
| --- | --- | --- | --- |
| 准入拒绝 | 格式不支持、超限、文件损坏、恶意内容信号、密码保护或不满足材料要求 | 标记 `rejected` 或转 `changes_requested`；向提交者说明安全且可操作的重传/补件方式。 | 进入解析或 Agent 审核；把拒绝展示为审核结论。 |
| 解析失败 | 解析器错误、OCR 无法完成、无可用文本/结构 | 标记 `parse_failed`，保留最小诊断审计；根据可恢复性自动重试、提示重传或转人工。 | 以空文本继续审核；将失败表示为“无风险”。 |
| 解析质量不足 | OCR 置信度低、空页比例高、乱码多、文本覆盖率不足、定位不可靠 | 保留质量信号；要求清晰副本、允许人工核对，或限制为必须人工复核。 | 据此自动放行高风险或证据要求严格的规则。 |
| 基线不可用或冲突 | 无适用规则版本、规则范围不匹配、版本在运行中失效 | 阻止产生可交付结论；转策略/人工队列，并向提交者提示“审核规则确认中”。 | 静默替换规则；用不明基线继续得出结论。 |
| Agent 失败 | 超时、限流、调用错误、结构化输出无效、证据校验失败 | 标记 `agent_failed`；进行有界系统重试，仍失败则建立人工待办或受控重试队列。 | 把空发现项当作通过；隐藏失败后直接交付。 |
| 结果冲突或不确定 | 高严重度、低置信度、无定位证据、跨规则冲突、提交者异议 | 分流至 `human_reviewing`，携带冲突说明和完整证据包。 | 仅以模型摘要自动关闭。 |
| 并发重提/版本冲突 | 重复提交、相同幂等标识、原件或基线变化 | 关联或拒绝重复请求；将新材料作为新版本，并保留旧运行只读。 | 覆盖历史文档、结果或人工决定。 |

## 6. 重试、补件与升级

### 6.1 重试分类

系统只对瞬时、非内容性的故障执行有界自动重试，例如短暂的服务超时、限流或暂时不可用。每次重试必须写入审计事件，关联同一文档版本、同一审核基线和同一运行；达到上限后，状态必须明确变为失败或等待人工处理，不能无限停留在“处理中”。

以下情况不应由系统盲目重试，而应要求提交者处理或人工判断：文件加密、文件损坏、扫描质量不足、缺失附件、版本不明、规则范围不匹配、无可定位证据、规则冲突和安全风险信号。内容变更后的任何再次处理均为新版本或新运行，不是对失败运行的“覆盖式重试”。

### 6.2 补件与重提

补件请求由人工审核者或材料准入规则发起，并至少包含：待补的材料/需修改事项、请求原因的可见摘要、关联文档版本、负责方、创建时间和提交方式。若请求源自风险项，提交者看到的是经可见性策略过滤后的业务说明，不应接收内部模型提示、其他方敏感信息或未核实的推断。

提交者补件或修改合同后，系统应：

1. 接收材料并生成新的文档版本或明确关联的补件版本；
2. 将旧版本、旧解析结果、旧审核运行和旧人工决定保留为只读历史；
3. 依据新版本和当前获准基线创建新的解析/审核运行；
4. 在时间线中标明“因补件/修改而重新审核”，不得将旧运行结果作为新版本结论；
5. 仅在新运行完成相应分流与人工处置后交付新结论。

### 6.3 强制升级条件

满足任一条件时，系统必须创建或维持人工待办，不能仅依赖自动重试：红线或高严重度风险；低置信度、无证据定位或结论冲突；解析质量不足；解析/Agent 服务在有界重试后失败；审核基线不可用或失效；提交者异议；需要风险接受或例外批准；文档语言、类型或适用范围超出已验证边界。

升级后的责任状态应从系统处理切换为人工待办。提交者看到“正在人工复核”或“等待规则确认”等真实但不泄露内部细节的描述；审核者队列中必须显示升级原因、优先级、已尝试的恢复动作和相关版本。

## 7. 通知边界

| 事件 | 应通知对象 | 通知内容 | 不应包含 |
| --- | --- | --- |
| 材料接收/处理开始 | 提交者 | 已接收、当前阶段、案件标识和查看入口。 | 审核结论、其他案件信息。 |
| 需要补件或修改 | 提交者及负责审核者 | 所需动作、材料/修改项、关联版本、提交入口和状态。 | 内部模型轨迹、安全检测细节、未核实推断。 |
| 可恢复的后台重试 | 审核者/运营监控按阈值 | 阶段、影响范围、重试摘要和是否需要关注。 | 将临时技术抖动作为提交者的待办。 |
| 重试耗尽、质量异常或人工升级 | 负责审核者；提交者按其是否需行动决定 | 审核者得到原因和证据上下文；提交者得到“正在人工复核”或可执行补件请求。 | 未授权原文、模型细节、其他人员信息。 |
| 人工决定已形成或交付 | 提交者和相关审核者 | 经授权的决定摘要、后续动作、交付入口。 | 未交付的内部意见、无权限风险项。 |

通知是状态变化的提醒，不是状态事实的唯一载体；权威状态以案件详情时间线和审计记录为准。重复、延迟或未送达通知不得改变案件状态，也不得触发自动批准或关闭。

## 8. 角色职责与人工审核交接

| 角色 | 中间状态职责 | 权限边界 |
| --- | --- | --- |
| 业务提交者 | 上传、查看授权范围进度、补件、修改后重提、对结果提出异议。 | 不得修改原有证据、历史决定或查看内部运行细节。 |
| 前端 | 以面向角色的方式展示状态、下一步、错误提示、补件与证据定位入口。 | 不判断合规性，不自行推导状态，不保存服务端密钥。 |
| 后端/编排器 | 执行状态转移、幂等控制、重试编排、授权检查、审计记录和队列分流。 | 不将客户端请求直接视为人工决定，不覆盖历史记录。 |
| 解析/OCR 服务 | 生成标准化文本、定位与质量信号，报告可恢复或不可恢复失败。 | 不作合规结论或最终决定。 |
| Agent | 在版本化基线下生成附证据的候选风险，报告失败和不确定性。 | 不拥有审批权，不执行文档中的指令。 |
| 法务/合规审核者 | 接手强制升级事项，确认、改判、要求补件、拒绝、接受风险或升级专家，并记录理由。 | 不得无证据批量确认高风险结论。 |
| 策略负责人/管理员 | 处理基线失配、队列运行、权限和质量治理；审阅趋势。 | 不静默改写完成案件的规则、结果或法务决定。 |

### 8.1 Agent 到人工的交接包

进入人工队列时，系统应提供：案件和文档版本标识、审核基线版本、当前状态和升级原因、解析质量与失败/重试摘要、风险项及其严重度/置信度、原文定位和上下文、关联规则依据、候选建议、历史补件与人工决定、提交者异议（如有）以及完整的状态时间线。

交接包必须先呈现原文证据和规则依据，再呈现候选结论。若 Agent 或解析未能生成可靠证据，界面必须显式标识“证据不足/不可用”，并将其作为人工判断事项，而不是用空白代替。

### 8.2 人工决定后的回流

审核者可选择确认风险、改判/标记误报、请求补件、标记解析问题、升级专家、拒绝或在授权范围内批准。每个决定都应记录操作者、时间、理由、关联版本和关联风险项/案件；改判、风险接受及高风险确认尤其需要理由。

人工请求补件时，案件转入 `changes_requested`；提交者重提后创建新版本和新运行。人工升级专家时，案件保持人工处理路径，不回退为 Agent 自动结论。只有所有需要处置的事项已按权限完成决定，且结果满足交付策略时，案件才能进入 `approved` 和/或 `delivered`。

## 9. 风险、待确认事项与下一阶段交付物

待确认的产品与治理决策包括：不同合同类型/语言的解析质量阈值；自动重试上限及何时通知；补件材料清单和时限；各角色的案件与证据可见范围；可使用的通知渠道；专家升级的服务时限；以及是否存在经明确授权的低风险自动放行范围。

下一阶段应将本规范转化为可验证的状态机、案件/运行/待办 API 契约、错误码和通知模板、人工审核队列与补件界面原型、权限矩阵，以及覆盖失败、重试、版本替换和人工交接的端到端测试场景。任何对自动放行、规则适用范围、外部通知或数据访问范围的扩展，都应先更新相应计划和业务规则。
