# 上传、材料准入与解析任务创建交互链路

## 1. 目标、范围与非目标

本链路把业务提交者的合同材料提交转化为可追溯、可解析且可供后续审核使用的文档版本。目标是：在进入审核基线匹配和 Agent 审核前，明确材料是否齐全、文件是否安全且可读、解析结果是否足以支持原文证据定位，并向用户提供可行动的状态和补件指引。

范围覆盖创建审核案件、选择允许的审核范围、上传合同正文及附件、上传前后校验、异步解析任务创建、解析质量分流、补件和重提。不在本链路中定义数据库表、API 字段、对象存储实现、反恶意引擎、OCR/解析器细节、审核基线选择算法、Agent 审核逻辑或最终法务决定。

本链路不产生“审核通过”结论。`rejected`、`parse_failed`、安全隔离和材料待补都不是批准或放行；只有后续具备权限的人工审核者可作出业务批准决定。

## 2. 业务输入、假设与边界

### 2.1 已继承的业务输入

本设计以 `docs/03_business_problem_modeling/document_audit_business_model.md` 为准，继承以下约束：

- 审核案件是一次业务请求的生命周期容器；每次提交形成独立的文档版本，历史版本与历史运行只读保存。
- 合同正文、附件、版本身份、可读性、适用范围是审核准入条件；不满足时应补件或转人工，不能进入 Agent 审核。
- 解析结果必须支持页码、段落、表格或坐标等原文定位，并携带解析质量信号。
- 高影响事项和质量/安全异常必须显式分流，由人工处理；文档内容属于不可信输入，不能改变服务端规则或触发外部操作。

### 2.2 MVP 假设

- 初期服务标准 NDA、标准采购或服务协议等规则成熟、范围清晰的合同类型。
- 提交者只能在已授权的案件中上传，并只可查看本人的授权范围内状态与后续结果。
- 支持格式、单文件大小、总大小、页数、语言、必备附件规则及数据保留期限由策略负责人配置；具体阈值不在本文件固化。
- 长文档解析采用异步任务。提交成功的回执代表材料已受控接收，不代表内容已经解析、可审核或被批准。

### 2.3 边界与待确认项

产品、法务和安全负责人需在实施前确认目标格式/语言、附件清单、重复文件规则、密码保护文件处置、恶意文件隔离流程、可接受处理时延、数据驻留与保留要求，以及何时允许人工豁免材料准入。任何自动放行规则均不属于本 MVP 默认行为，必须单独授权、版本化并记录。

## 3. 用户入口与提交路径

### 3.1 入口

业务提交者从“新建审核案件”进入。界面先说明审核范围、允许的材料类型、是否需要合同正文和附件、当前案件状态及隐私/保留提示；随后由用户：

1. 选择允许的合同类型、交易背景或审核范围；
2. 填写必要的业务上下文和版本说明；
3. 添加合同正文及相关附件；
4. 在上传清单中核对材料后提交；
5. 通过案件详情持续查看状态、失败原因、补件项及后续待办。

客户端仅辅助输入完整性和本地文件选择提示。案件权限、可用审核范围、必需材料、版本创建、任务状态、受控存储和审计记录均由服务端判定并保存。

### 3.2 文档角色与版本规则

- 每份文件必须标明材料角色：`primary_contract`（合同正文）或 `supporting_attachment`（支持附件）。同一文件不能以不明角色进入审核。
- 新上传、替换正文、补充附件、修订合同或更换审核范围时，均创建新的文档版本；不得覆盖已被解析或已进入审核运行的版本。
- 用户可为当前批次提供版本说明，但版本关系以服务端记录的案件、文档版本、文件哈希、提交人和时间为准。
- 相同文件哈希或重复提交只用于提示和幂等处理，不得擅自合并不同案件、不同权限范围或不同审核范围的材料。

## 4. 上传前校验

上传前校验用于尽早给出反馈，不能替代服务端校验。检查结果应逐项显示为“可继续”“需补充”“不可提交”及理由。

| 校验项 | 触发条件 | 用户可见处理 | 服务端结论 |
| --- | --- | --- | --- |
| 身份和案件授权 | 无登录、无案件访问权或不允许创建版本 | 提示无权限并引导联系案件所有者/管理员 | 拒绝创建或上传 |
| 审核范围 | 未选择、已失效或用户无权使用的合同类型/范围 | 要求重新选择可用范围 | 不创建可审核版本 |
| 材料完整性 | 缺合同正文、必需附件或必要业务信息 | 清单标出缺少项，允许继续暂存但不能提交审核 | 转材料待补，不启动解析 |
| 文件选择 | 格式、声明大小、单批总量或页数超过策略上限 | 在选择时列出不合格文件和限制说明 | 仍须在接收后复核 |
| 重复风险 | 与当前批次或近期版本文件名/哈希相同 | 明示“可能重复”，供用户选择继续、替换或取消 | 使用幂等键和版本规则裁决 |

上传前通过只代表可以开始传输。浏览器声明的文件类型、大小、页数、病毒状态和可读性均不得作为最终信任依据。

## 5. 上传后校验与准入分流

文件到达受控接收区后，服务端完成以下校验。未完成全部必要校验前，文件不得提供给解析服务、审核 Agent 或其他用户下载。

| 校验类别 | 最低判断 | 通过后的动作 | 不通过后的动作 |
| --- | --- | --- | --- |
| 完整性与幂等性 | 上传是否完整；上传令牌、案件、版本和幂等键是否一致 | 固化接收回执和文件身份 | 中止本次接收；可安全重试时提示重传 |
| 文件真实性 | 文件签名、实际 MIME/容器结构与声明类型是否一致 | 允许进入安全检查 | 拒绝该文件，说明格式不受支持或文件类型不一致 |
| 策略上限 | 实测大小、页数、压缩/解压规模、附件数是否合规 | 允许进入安全和可读性检查 | 拒绝或要求拆分/缩减；不启动解析 |
| 安全检查 | 恶意文件、危险嵌入对象、异常压缩包、受密码保护或不可安全处理的内容 | 将原件标记为可处理 | 隔离并停止后续处理；仅展示安全的通用说明，不暴露安全规则细节 |
| 可打开性 | 解析器能否安全打开文件、是否损坏或空文件 | 创建解析任务 | 标记不可解析，提示用户重新导出或上传可读版本 |
| 材料与范围一致性 | 正文/附件角色、必需材料、版本说明及审核范围是否满足准入 | 将版本标记为 `accepted` | 创建补件待办或拒绝本版本；不进入 Agent |

校验通过后，系统记录最小必要审计信息：案件与文档版本标识、原文件哈希、材料角色、提交者与时间、声明及识别后的文件类型、策略版本、校验结论和状态变更原因。原件与后续派生文本分开管理，但须采用等同或更严格的访问控制。

## 6. 解析任务创建与状态编排

### 6.1 创建规则

当一个文档版本的必需材料均为 `accepted`，且不存在未解决的安全隔离、材料缺失或策略冲突时，服务端为该版本创建一次解析任务，并写入状态事件。任务必须绑定：案件、文档版本、原件身份/哈希、材料角色、解析器/OCR 版本、请求幂等键和创建时间。

任务由异步队列执行。创建任务后即返回案件/版本标识和当前状态；不保持上传请求等待 OCR 或长文档解析完成。若重复请求携带相同幂等语义，应返回已有任务或明确的冲突结果，不能产生并行且相互覆盖的解析结果。

### 6.2 解析输出与质量门槛

解析服务应生成供后续审核与人工复核使用的标准化表示，包括可提取文本、页与段落/表格结构、原文定位锚点、必要的页图引用和质量信号。扫描件走 OCR，但 OCR 文本仍需标记来源与置信质量。

解析质量至少评估：文本覆盖率、空页/乱码比例、OCR 置信度、页码对应性、结构提取完整度及语言/格式是否在已验证范围。质量达标的版本进入 `ready`；低质量但可继续处理的版本不得静默视为正常，应转人工准入或补件；无可用解析结果则为 `parse_failed`。

### 6.3 本链路状态

```text
created
  → uploading
  → accepted
  → parsing
  → ready
```

异常和返回路径：

```text
uploading / accepted → rejected                 （格式、上限、安全或准入不通过）
accepted → materials_requested                  （材料缺失、版本/范围信息不足）
parsing → parse_failed                          （无法安全或有效解析）
parsing → manual_intake_review                  （可读但质量不足或规则冲突）
materials_requested / parse_failed / rejected
  → resubmitted → uploading                     （提交者提供新文档版本）
```

`materials_requested` 与 `manual_intake_review` 是本交互链路为清晰分流所需的案件级/版本级可见子状态；实现时应与业务模型定义的 `changes_requested`、`resubmitted` 通过状态映射保持一致，且每次状态迁移均记录原因、操作者/系统主体和时间。`ready` 仅表示材料与解析结果已准备就绪，不表示已经匹配基线、进行 Agent 审核或获得结论。

## 7. 用户可见状态与反馈

提交者始终可在案件详情看到当前版本、材料清单、最后更新时间、下一步和受权限控制的错误原因。状态文案必须避免暗示法律评价或审批结果。

| 状态 | 面向提交者的含义 | 可执行动作 |
| --- | --- | --- |
| `created` | 案件已建立，尚未提交完整材料 | 补充信息和选择文件 |
| `uploading` | 文件正在安全接收 | 等待完成；网络中断后重试未完成文件 |
| `accepted` | 材料已接收并完成准入，准备或正在创建解析工作 | 查看材料清单；无需将其理解为审核完成 |
| `parsing` | 正在提取文本和结构，处理时长受文件质量和页数影响 | 查看进度/更新时间；可在策略允许时取消未开始的版本 |
| `ready` | 文档已可供下一审核阶段处理 | 查看“将进入审核准备”的说明；等待后续结果 |
| `materials_requested` | 缺少必要材料或版本/范围说明 | 根据清单上传补件或修订版本 |
| `manual_intake_review` | 文件可打开但质量或准入条件需要人工确认 | 等待审核者处理，或按要求提供更清晰材料 |
| `rejected` | 当前版本不能进入处理 | 查看安全的拒绝原因并上传新版本 |
| `parse_failed` | 当前版本无法生成可信解析结果 | 重新导出、提供更清晰扫描件或按指引补件 |
| `resubmitted` | 已提交新版本，旧版本保留为历史记录 | 跟踪新版本状态 |

系统可通过站内通知或其他获授权渠道提醒状态变化，但通知不得包含原文内容、内部安全检测细节、其他案件信息或未经发布的审核结果。

## 8. 异常、补件与重提

### 8.1 补件规则

材料缺失、附件角色不明、版本说明不足、范围不匹配或解析质量不足时，系统创建明确的补件待办。待办至少包含：所缺/需替换材料、原因类别、需要的可操作动作、对应案件和当前版本、提出时间、处理主体及截止时间（如业务策略要求）。

补件不应让提交者修改既有原件或历史解析结果。提交者上传替换件或新附件后，系统创建新文档版本并重新执行本链路；旧版本、其校验结论和任何已创建的任务保持可追溯且只读。

### 8.2 异常分流原则

- 网络中断、上传不完整：允许在有效令牌和策略范围内续传/重试；完成性未知时不得创建解析任务。
- 文件受损、不支持、超限：拒绝当前文件，给出格式、重导出或拆分等可行动建议。
- 密码保护、危险嵌入对象或恶意文件信号：立即隔离、停止自动处理，并按安全流程通知有权限的管理员；不得尝试绕过保护。
- OCR/解析质量低：要求重扫或转人工准入；任何后续自动化均须受到质量信号约束，不能把空文本或低质量文本当作“未发现风险”。
- 解析超时、服务不可用或无效输出：进行有界重试并保留失败原因；重试耗尽后标记 `parse_failed` 或转人工，不把空结果视为成功。
- 并发或重复提交：以案件、版本、幂等键和哈希进行服务端裁决；用户界面清楚标识新旧版本，禁止结果覆盖。

## 9. 角色职责与权限边界

| 角色 | 在本链路中的职责 | 不可承担的职责 |
| --- | --- | --- |
| 业务提交者 | 创建案件、提供授权范围内的材料和说明、响应补件、查看授权状态、提交新版本 | 改写证据/历史结果、绕过准入、查看他人案件、作出法务批准 |
| 前端 | 提供入口、文件清单、进度、可操作提示和版本对比入口；调用受权限保护的服务 | 作为可信校验主体、决定准入、保存服务端密钥、直接访问内部存储 |
| 后端/API | 鉴权、案件/版本/任务编排、服务端校验、幂等、审计、结果可见性与状态机控制 | 用客户端判断替代安全控制，或将不可信原文直接授予广泛工具权限 |
| 解析/OCR 服务 | 受控地提取可定位文本和结构，返回质量信号及明确失败 | 判断法律风险、批准案件或修改源文件 |
| 法务/合规审核者 | 对低质量、范围冲突或例外准入进行人工判断，并提出可追溯补件要求 | 无证据地确认高风险审核结论，或覆盖历史版本 |
| 策略负责人/管理员 | 维护允许范围、材料策略、阈值、权限、保留和安全异常流程 | 静默改写已完成案件的校验结论或审核结果 |

## 10. 向下一链路的交接

仅状态为 `ready`、质量达到已定义最低门槛且无未解决准入待办的文档版本，可交接给“审核基线选择与审核准备”链路。交接包必须引用而非复制以下版本化输入：

- 案件、文档版本与材料角色标识；
- 受控原件身份和不可变哈希；
- 标准化解析表示、页/段落/表格/坐标等原文定位锚点；
- OCR/解析器版本、质量信号、语言/格式识别结果；
- 已确认的审核范围及提交者提供的必要业务上下文；
- 准入策略版本、校验结论、状态时间线和审计事件引用。

下一链路据此匹配明确版本和适用范围的模板、条款库及红线规则，并创建独立审核运行。不得因解析成功而默认选择规则，也不得让后续审核覆盖本链路的原件、版本、校验结论或审计记录。若文档、材料、范围或审核基线发生变化，应依照版本规则创建新的版本或新的审核运行。

## 11. 验证清单、风险与下一阶段交付物

### 11.1 交互验证清单

- 提交者能在单一案件内分辨合同正文、附件、当前版本和历史版本。
- 服务端对伪造类型、超限、损坏、受保护、恶意或不完整文件均阻止其进入解析/审核。
- 缺材料、解析质量不足、解析失败与安全隔离均有不同且可行动的用户反馈，不显示为通过。
- 相同请求的重试不会生成冲突的文档版本或解析任务；新版本不会覆盖历史记录。
- `ready` 版本可提供可定位解析结果和质量信号；不达标版本无法进入基线匹配和 Agent 审核。
- 状态变更、补件、重试、失败和人工准入动作均可审计并受角色权限约束。

### 11.2 关键风险

主要风险是将“上传成功”误解为“审核通过”、将低质量 OCR 误作可信原文、因重复上传覆盖历史结果，以及不可信文档内容影响自动化行为。实施时应以服务端状态机、版本不可变性、质量门槛、最小权限、受控存储和证据定位校验作为控制措施。

### 11.3 下一阶段交付物

本链路为后续“审核基线选择与准备”“Agent 候选风险生成”“人工复核与风险处置”提供版本化输入和状态契约。后续阶段应进一步定义审核准备状态、基线适用性判定、审核运行创建条件、风险证据包，以及面向提交者与审核者的结果交付交互。
