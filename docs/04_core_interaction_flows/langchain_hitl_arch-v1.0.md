## 2. 职责覆盖与交接映射

| 交接阶段 | 后端服务规范的既有职责 | HITL 架构规范的既有承接 |
| --- | --- | --- |
| 上传与解析准备 | 受控接收材料，判定准入，创建文档版本与解析任务，生成可定位解析结果和质量信号。 | 只有当前版本准入通过、解析可用且已固定审核基线时，才可创建可暂停/恢复的审核运行。 |
| 审核运行与分流 | 固定文档版本和审核基线，维护候选风险、证据、运行状态和人工路由结果。 | 以“文档版本 + 审核基线 + 审核运行”为 HITL 流程边界，在既有人工触发条件处暂停。 |
| 人工复核与恢复 | 查询并提供当前版本、运行、风险、证据、质量/异常摘要、路由原因与历史；校验权限和责任。 | 人工输入仅能在同一有效上下文下恢复；恢复前仍由后端校验权限、责任、版本、运行、证据与状态。 |
| 决定、交付与重提 | 保存追加式人工决定、状态转换和审计事件；新材料或基线变化创建新版本/运行。 | checkpoint 只用于图执行恢复，不替代业务审计；版本/基线变化使旧暂停流程不可恢复，转入新运行。 |

## 3. 共同约束索引

- 服务端是案件、版本、运行、风险、决定及审计事件的权威维护方；前端只发起经用户确认的操作并展示授权结果。
- Agent 输出、解析成功或空风险项均不等同于 `approved`；案件级批准由有权限人员对当前有效上下文作出。
- 高严重度、低置信度、无证据、解析质量异常、规则冲突和提交者异议按既有规则进入人工路径。
- 历史版本、运行、候选结果与人工决定只读保留；不得以新的材料、基线或决定覆盖历史。
- HITL 中断恢复会触发节点从开头重执行，因此具体实现阶段需遵守来源文档中的副作用幂等、待办去重和通知去重要求。

## 4. LangChain MCP 调研记录

来源 HITL 规范明确：**LangChain MCP 的主要作用是获取 LangChain 官方最新的文档规范**，而不是文档审核的运行时编排器，也不替代 LangGraph 的 `interrupt`、checkpoint、恢复或业务审批控制。

本次 Teammate 调研尝试使用项目已配置的 LangChain 官方文档 MCP；当前会话未暴露对应可调用工具，重试后仍不可用。详细限制、官方复核链接及“进入具体 SDK/API 实施前必须再次核验”的要求均保留在 [LangChain HITL 文档审核流程架构规范 v1.0](../06_system_architecture/langchain_hitl_document_audit_arch-v1.0.md) 中。
