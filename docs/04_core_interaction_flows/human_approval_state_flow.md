# 人工审批状态交互链路

## 1. 目标、适用范围与非目标

本规范定义 DocAuditAgent 在审核案件进入人工复核后，如何让具备相应权限的人员基于可复核证据完成决定、协作和交付。重点是把人工决定约束为与具体文档版本、审核运行和证据包绑定的可追溯动作，避免以模型摘要或历史结论直接放行当前合同。

适用范围是 MVP 中 NDA、标准采购／服务协议等规则成熟的合同类型，覆盖以下人工处置：同意、编辑、驳回、要求补件、转交和升级。

本规范不定义页面布局、接口、数据表、通知通道、权限系统技术实现或自动化审批。它不赋予产品输出法律意见、自动批准合同例外或自动放行高风险签约的能力。

## 2. 输入、假设与边界

### 2.1 业务输入

本规范继承 `docs/03_business_problem_modeling/document_audit_business_model.md` 的业务语义：

- 审核案件包含一个或多个文档版本；每次审核运行固定引用一个文档版本和一个版本化审核基线。
- 风险项必须关联原文定位、上下文、适用依据、严重度、置信度和建议动作；证据不足的候选结论不能作为放行依据。
- 红线、高严重度、低置信度、解析质量异常、规则冲突和提交者异议必须进入人工队列。
- 人工决定关联案件或风险项，并记录责任人、理由和时间；原文或基线变化必须产生新的版本或运行，旧结果只读保留。

### 2.2 设计假设

- 审批是人工专业判断，不等同于 Agent 的建议，也不能由无审批权限的提交者完成。
- 案件级结论以当前有效审核运行中所有需处置风险项均已满足交付条件为前提。
- 一个案件可有多个风险项并行处理；但同一案件的最终批准、驳回、补件和交付须以一个明确的当前责任人和状态为准。
- 编辑是对人工判断或处置意见的修订，不得改写原始文件、原始证据、Agent 输出或历史决定。

### 2.3 状态边界

沿用案件业务状态 `triaged`、`human_reviewing`、`approved`、`changes_requested`、`rejected`、`delivered`、`resubmitted`、`archived`。本规范仅补充这些状态在人工环节的进入条件和转换约束；不改变上传、解析和 Agent 执行的内部状态。

风险项另有处置语义：`pending_human_decision`、`confirmed`、`modified`、`rejected_as_false_positive`、`supplement_required`、`transferred`、`escalated`、`accepted_with_authorization`。风险项状态用于表达局部处置，不能单独取代案件级交付结论。

## 3. 审批入口

### 3.1 进入人工队列的条件

审核运行完成并聚合风险后，案件进入 `triaged`。满足任一条件时，系统将案件路由至人工复核队列，并将案件置为 `human_reviewing`：

- 命中红线或高严重度风险；
- 存在低置信度、无可定位原文证据或解析质量异常的结论；
- 审核基线或规则出现冲突、失效或适用范围不明；
- 提交者对结果提出异议；
- 审核者主动要求人工复核或重新分流。

材料不完整、不可读、版本不明或不适用时，不应伪装成审批待办：案件应通过准入链路进入补件或人工处理，且不得生成推断性批准结论。

### 3.2 队列接收与责任确认

队列应展示案件标识、当前文档版本、合同类型、风险摘要、最高严重度、触发原因、当前审核基线、等待时长和当前责任。接收审批任务时，审核者确认其为当前责任人；转交或升级后，原责任人不再拥有最终决定权，除非任务被显式退回。

进入案件详情后，审核者必须先确认当前文档版本和审核运行仍有效。若已有新版本、运行失败、证据包不完整或权限不再满足，最终决定入口应被阻止，并进入相应的异常路径。

## 4. 审批证据包

人工审批页以案件的当前有效审核运行为唯一上下文，至少提供下列证据包：

| 组成 | 必须内容 | 审批用途 |
| --- | --- | --- |
| 案件上下文 | 案件标识、合同类型、提交目的、参与方、提交者、当前状态与责任人 | 确认业务范围与责任归属 |
| 文档与版本 | 当前文档正文、附件清单、版本标识、来源、提交时间与版本差异提示 | 防止基于旧版文本作出决定 |
| 原文证据 | 风险原文定位、上下文摘录、定位可用性与解析质量信号 | 支持回读和专业判断 |
| 风险项 | 分类、严重度、置信度、建议动作、当前处置、相互冲突或依赖关系 | 逐项完成处置并判断案件是否可交付 |
| 审核依据 | 模板、条款库、红线规则、适用范围及各自版本 | 说明为什么此条款构成偏离或风险 |
| 过程历史 | 已有人工决定、编辑差异、补件记录、转交/升级链、提交者异议 | 避免重复判断并还原责任链 |
| 交付预览 | 对提交者可见的结论、待办、风险摘要及受限信息标识 | 确认最终交付不泄露内部信息 |

证据包缺少原文定位、适用依据或当前版本关联时，相关风险项必须标为待人工确认；若缺失使案件级判断失去基础，则不能同意或交付。

## 5. 人工动作与状态转换

### 5.1 总体转换

```text
triaged → human_reviewing
human_reviewing ─同意→ approved → delivered
human_reviewing ─要求补件→ changes_requested → resubmitted →（新版本/新运行）→ triaged
human_reviewing ─驳回→ rejected
human_reviewing ─转交→ human_reviewing（责任人变更）
human_reviewing ─升级→ human_reviewing（升级队列/更高权限责任人）
approved / rejected / delivered ─更正或新增版本→ resubmitted →（新运行）→ triaged
```

所有从 `human_reviewing` 触发的决定都应先校验：操作者权限、当前任务责任、文档版本、审核运行、证据完整性以及并发状态。状态改变成功后，原状态、目标状态、操作依据和对象版本一并留痕。

### 5.2 同意

“同意”表示审核者已完成当前有效运行中所有必要风险项的人工处置，并依授权范围作出案件级人工批准。它不是“合同无风险”，也不自动代表签署授权。

- 前置条件：当前文档和基线未变化；所有红线、高风险及待人工确认事项已被处置；所需风险接受已取得对应授权；证据包可复核。
- 必填内容：案件级决定理由、必要的风险条件/限制、所引用的风险项及授权记录。
- 转换：案件从 `human_reviewing` 到 `approved`；可交付信息审核无误后，从 `approved` 到 `delivered`。
- 限制：不能以仅有摘要、缺失定位证据或旧运行结果完成同意。

### 5.3 编辑

“编辑”用于修订人工对风险项的判断、严重度、建议动作、交付说明或案件级意见，例如将候选风险标记为误报、补充限制条件，或改判风险等级。

- 前置条件：操作者对目标风险项或案件拥有相应复核权限，且当前版本/运行有效。
- 必填内容：编辑前值、编辑后值、改判理由及支持证据或依据引用。
- 转换：风险项可由 `pending_human_decision` 转为 `confirmed`、`modified` 或 `rejected_as_false_positive`；案件保持 `human_reviewing`，直至满足其他终态条件。
- 限制：编辑产生新的人工决定记录；不得覆盖 Agent 原始候选结果、原文证据、审核基线或历史决定。

### 5.4 驳回

“驳回”表示审核者拒绝当前案件的审核请求或拒绝当前文本在既定基线下继续获得批准。它应区分“无法在现有条件下批准”和“材料不合格需补件”：后者使用要求补件。

- 前置条件：驳回依据已在证据包中明确，且操作者具备案件级驳回权限。
- 必填内容：驳回范围（案件或特定风险接受）、具体理由、相关风险项/规则证据，以及对提交者可行动的后续说明。
- 转换：案件从 `human_reviewing` 到 `rejected`；未完成的风险项保持历史可见但不可被误认为已批准。
- 后续：提交者若以修订合同重新发起，应生成新文档版本及新审核运行，案件进入 `resubmitted` 后再回到 `triaged`。

### 5.5 要求补件

“要求补件”用于当前文档、附件、版本身份、交易背景、授权材料或原文可读性不足，导致无法可靠判断的情形。

- 前置条件：审核者明确指出缺失项及其与判断的关系；不得以泛化描述代替可执行待办。
- 必填内容：缺失材料/修改要求、目的、适用风险项、截止或优先级（如业务另行定义）、是否需要重新审核。
- 转换：案件从 `human_reviewing` 到 `changes_requested`；相关风险项转为 `supplement_required`。
- 重提：提交者补交或修改后，案件进入 `resubmitted`，必须创建新的文档版本；系统对新版本建立新审核运行并重新 `triaged`。旧版本、旧证据和旧决定保持只读。

### 5.6 转交与升级

“转交”用于把任务交由另一名具有相近或特定专长的审核者处理；“升级”用于红线、超授权风险、重大规则冲突、关键异议或需更高决策层级的事项。

- 前置条件：选择目标人员或目标队列，并确认其对案件范围具有访问权限；不能以转交规避已作出的责任记录。
- 必填内容：转交/升级原因、待解决问题、目标角色或队列、需要其处理的风险项、当前证据包版本及紧急程度（如适用）。
- 转换：案件保持 `human_reviewing`；风险项分别转为 `transferred` 或 `escalated`，当前责任人更新为接收者。接收者可继续编辑、补件、驳回或同意。
- 限制：转交不改变文档版本、审核基线或既有决定；升级完成前，原角色不得越权作出案件级最终批准。

## 6. 权限与职责

| 角色 | 可执行动作 | 明确限制 |
| --- | --- | --- |
| 业务提交者 | 创建案件、补交材料、查看其授权范围内的状态、交付结果和补件待办、提出异议、重提 | 不得修改证据、基线、人工决定或作出法务审批 |
| 法务／合规审核者 | 接收任务、查看证据包、编辑风险判断、要求补件、在授权范围内同意或驳回、转交/升级 | 不得基于无证据结论批准，不得超越风险接受或签署授权范围 |
| 专家／上级审批者 | 处理升级事项、作出其授权范围内的风险接受、最终同意或驳回、退回任务 | 不得改写历史决定或绕过版本重审要求 |
| 条款／策略负责人 | 解释或更新后续适用的模板、条款库、红线规则和适用范围 | 不得静默改变已完成运行使用的基线或替代案件审批决定 |
| 管理员／运营负责人 | 管理权限、队列、异常处置和保留策略 | 不得因系统管理权限而替代专业人员作出案件法务判断 |

权限应同时按角色、案件范围、合同类型、风险级别和审批额度（如业务定义）约束。失去访问权限、任务已转交或案件已进入终态的操作者，不得提交新的最终决定。

## 7. 异常、并发与不可逆操作

| 情形 | 处理规则 |
| --- | --- |
| 证据缺失、定位失效或解析异常 | 阻止同意和交付；要求补件、重新解析或升级人工判断，并记录缺失原因。 |
| 文档版本或审核基线在审批中变化 | 当前运行不再可作为新版本结论；冻结当前审批动作，创建或等待新运行，历史保持只读。 |
| 两位审核者并发操作 | 以最新有效责任和版本校验为准；冲突提交不得静默覆盖，应提示刷新、重新确认或由上级裁决。 |
| 接收者无权限或转交失败 | 保持原责任人和 `human_reviewing`，记录失败原因，不得造成无责任队列。 |
| 审核者撤回已保存决定 | 在尚未交付且未被后续决定依赖时，可按授权创建“撤回/更正”决定；原记录不可删除。 |
| 已批准、驳回或交付后发现错误 | 不直接覆盖终态；创建更正记录，并在需要时通过新文档版本或新审核运行重新进入 `resubmitted`/`triaged`。 |
| 审核运行失败或规则失效 | 不得自动视为通过；转为异常待办、重新运行或升级，并标明不可交付。 |

不可逆的原则是：原始文件、文档版本、审核运行、审核基线引用、Agent 候选结果和已保存的人工决定均只追加、不覆盖。后续更正通过新的决定、版本或运行表达。

## 8. 审计留痕

每个关键动作都生成不可变审计事件，并至少关联案件、文档版本和审核运行。事件应包括：

- 事件类型（接收、查看、编辑、同意、驳回、补件、转交、升级、撤回、更正、交付等）；
- 操作人、其角色及当时的授权上下文；
- 发生时间、原状态和目标状态；
- 目标对象（案件或风险项）、风险项标识及前后处置内容；
- 当前文档版本、审核基线版本、证据/原文定位与理由引用；
- 转交来源、接收者、升级层级和责任变更；
- 面向提交者的交付版本、可见内容范围及实际交付时间。

审计记录用于争议复核、版本回溯、责任链还原和质量改进。其呈现可受权限控制，但不得因界面隐藏而删除底层业务事实。

## 9. 结果交付

只有案件为 `approved` 且交付内容完成权限与完整性校验后，才可转为 `delivered`。交付应始终明确对应的文档版本、审核运行和交付时间，避免提交者将历史结果用于新文本。

提交者可见的信息按决定类型交付：

| 案件结果 | 提交者获得的内容 |
| --- | --- |
| 已同意并交付 | 人工审核结果、适用条件/限制、已处置风险的业务可行动摘要、对应文档版本。 |
| 要求补件 | 明确的材料或修改待办、关联目的和重提入口；不将未完成审核表述为通过。 |
| 已驳回 | 可对外展示的驳回原因和后续可行动建议；内部专业笔记、受限依据按权限隐藏。 |
| 已转交或升级 | 当前处理中、责任队列或预计动作（若业务定义），不泄露不必要的内部人员信息或内部讨论。 |

交付不能展示无权限案件、其他案件材料、内部审核讨论、受限策略细节或超出提交者知情范围的个人信息。提交者对结果提出异议后，案件应重新进入人工处理路径，且异议本身纳入审计记录。

## 10. 后续阶段交付与待决风险

本规范向后续阶段提供以下输入：

- 原型阶段：人工队列、证据包、风险处置面板、确认提示、补件待办、转交/升级和交付状态的页面语义。
- 架构、数据模型与 API 阶段：案件/风险项双层状态、责任转移、版本不可变、决定追加、权限校验、审计事件和交付可见性要求。
- 测试阶段：按动作、角色、版本变化、证据缺失、并发冲突和终态更正建立验收场景。

待后续明确的风险包括：不同合同类型的审批额度和签署授权矩阵、补件 SLA 与提醒机制、多人会签规则、外部身份/通知集成、已交付更正的通知和法律保留期。这些问题在未完成明确业务规则前，不应通过默认自动化处理。
