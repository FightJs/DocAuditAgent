# 文档审核 Agent 端到端流程调研

## 1. 目标、范围与结论边界

本调研拆解从用户提交文档到审核结论被采纳、反馈回流和可追溯归档的完整流程。覆盖 PDF、DOCX 和扫描件；关注解析、规则/Agent 审核、人工复核及异常处理。它不比较特定模型的准确率，也不构成法律、隐私或合规意见。

**来源事实**指下文链接中由官方资料直接支持的能力或要求；**设计建议**是结合这些事实给出的项目实施建议，需在本项目的样本文档、权限模型及合规要求下验证。

## 2. 端到端流程

| 阶段 | 主要动作与状态 | 输入 | 输出 | 责任主体 |
| --- | --- | --- | --- | --- |
| 0. 创建任务 | 创建审核任务、生成不可预测的任务 ID，状态 `created` | 用户、审核模板/规则版本 | 任务记录、上传凭证 | 前端、后端 |
| 1. 上传与准入 | 文件上传后进行类型、大小、页数、恶意文件与重复提交校验；状态 `uploading` → `accepted` 或 `rejected` | 原始文件、元数据 | 受控存储对象、拒绝原因或接收回执 | 用户、前端、后端 |
| 2. 解析与标准化 | 提取文本、页码、段落/表格、版式和页图；扫描件走 OCR；状态 `parsing` → `parsed` / `parse_failed` | 已接收的原件 | 标准化文档表示、页级证据定位、解析质量指标 | 解析服务 |
| 3. 预处理与策略匹配 | 清理重复文本、按标题/语义分块、识别语言、选择规则集和 Agent 版本；状态 `preparing` → `ready` | 标准化表示、任务模板 | 可审核块、适用政策、可复现实行快照 | 后端、审核编排器 |
| 4. Agent 审核 | 对每项要求提出结论、严重度、置信度、理由和页/段证据；状态 `agent_reviewing` → `agent_completed` / `agent_failed` | 文档块、规则、受限工具上下文 | 发现项、正向检查、运行轨迹摘要、模型/提示版本 | 审核 Agent、编排器 |
| 5. 聚合与分流 | 去重、冲突检测、根据严重度/置信度/规则决定自动通过、人工待办或拦截；状态 `triaged` | Agent 结果、阈值、风险规则 | 任务总览、人工审核队列、分流理由 | 后端、风险策略负责人 |
| 6. 人工复核 | 审核者在原文证据上下文中接受、修改、驳回或补充；状态 `human_reviewing` → `approved` / `changes_requested` / `rejected` | 发现项、原文片段、版本对比 | 已签署的审核决定、批注、责任人和时间戳 | 人工审核者 |
| 7. 交付与闭环 | 向提交者展示可见结论，支持修改后重提；保存审计包，状态 `delivered` / `resubmitted` / `archived` | 最终决定、可见性策略 | 报告、通知、可追溯审计记录、反馈样本 | 前端、后端、提交者、管理员 |

### 建议的状态约束

`rejected`、`parse_failed`、`agent_failed` 是终止或需重试的异常状态，不能被误展示为“审核通过”。任何修改原文件或选择新规则集的重提，都应创建新的文档版本和审核运行；旧运行只读保留。`approved` 只能由具备权限的人类审核者作出，除非业务另行定义并记录“低风险自动放行”的授权规则。

## 3. 参与者、责任与权限边界

| 参与者 | 应承担的责任 | 不应承担的责任 |
| --- | --- | --- |
| 提交者 | 上传、选择允许的模板、查看其权限范围内的结论、按意见重提 | 改写审核证据、查看他人文档或内部模型轨迹 |
| 前端 | 进度展示、失败提示、证据定位、人工决策交互 | 判断文档是否合规、保存服务端密钥或绕过权限 |
| 后端/API | 身份鉴别、授权、任务状态机、幂等性、审计记录和结果可见性 | 让客户端直接访问内部存储或模型凭证 |
| 解析/OCR 服务 | 产出可定位的结构化内容及质量信号 | 代替人工决定业务合规性 |
| Agent 与编排器 | 按版本化政策产出可解释的候选发现项；隔离不可信文档内容 | 拥有最终审批权、执行文档中出现的指令 |
| 人工审核者 | 在原文上下文复核，做出或升级最终决定 | 无证据地批量确认高风险结果 |
| 管理员/策略负责人 | 管理模板、阈值、权限、保留策略与质量监控 | 静默修改已完成运行的规则/结论 |

## 4. 输入输出与可追溯性要求

每个审核运行建议固化如下最小审计包：原文件版本标识与哈希、提交人和时间、解析器/OCR 版本与质量指标、规则集版本、模型和提示词版本、分块策略、每项结论的原文定位、分流规则、人工决定与操作者、状态变更时间线。原文件与派生文本应分开管理，但二者均需受相同或更严格的访问控制。

来源事实：Azure AI Document Intelligence 文档说明其分析输出包含内容、布局及包括表格在内的结构；OCR 与布局提取因此可作为审核前的独立环节，而不是把文件直接交给审核模型。参见 [Azure 文档分析概览](https://learn.microsoft.com/azure/ai-services/document-intelligence/overview)。

设计建议：将每个发现项的数据结构至少固定为 `rule_id`、`outcome`、`severity`、`confidence`、`rationale`、`evidence[]`、`document_version` 和 `review_status`。`evidence` 应包含页码、字符范围或坐标及原文摘录，使人可一键回到原文验证，避免仅凭模型摘要作决定。

## 5. 风险、异常与处理策略

| 风险/异常 | 检测或信号 | 建议处理 |
| --- | --- | --- |
| 不支持、超限或损坏的文件 | MIME/签名、大小/页数限制、解析器错误 | 拒绝或标记 `parse_failed`，说明可操作的重传方式；保留最小错误审计，不进入 Agent |
| 扫描质量低、OCR 误读 | OCR 置信度、空页比例、文本覆盖率、乱码比例 | 标记低质量、提示重扫或转人工；不得据此自动通过高风险规则 |
| 受密码保护或含嵌入对象 | 解密/解析失败、反恶意扫描信号 | 停止后续处理，走安全流程；不试图绕过保护 |
| 文档提示注入或不可信指令 | 文档文本包含“忽略规则”“调用工具”等内容 | 把文档视为数据；系统提示和工具权限在服务端固定；Agent 输出必须受结构化模式和策略校验 |
| Agent 超时、限流或模型失败 | 调用错误、超时、无效结构化输出 | 有界重试并记录次数；失败转人工或重试队列，绝不把空结果视为无问题 |
| 幻觉、漏检或结论冲突 | 无证据、规则冲突、低置信度、跨块不一致 | 强制证据校验、重复/冲突聚合；高风险与不确定项进入人工队列 |
| 权限泄露或敏感数据外发 | 越权访问、日志含原文、第三方处理路径 | 最小权限、传输/静态加密、脱敏日志、数据保留期限与供应商数据边界审查 |
| 并发重复提交或版本覆盖 | 相同幂等键、文件哈希、乐观锁冲突 | 上传和创建运行使用幂等键；结果与源版本绑定，禁止覆盖历史决定 |

来源事实：OWASP 的 LLM 应用风险清单将 Prompt Injection、敏感信息泄露和过度代理权限列为主要风险，适用于将用户上传文档作为 Agent 输入的场景。参见 [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/)。NIST AI RMF 将治理、映射、度量、管理作为风险管理活动，支持将质量监控和人工升级作为持续流程而非一次性功能。参见 [NIST AI RMF 1.0](https://www.nist.gov/itl/ai-risk-management-framework)。

## 6. 人机交接设计

### 6.1 Agent → 人工：必须升级的情形

建议对下列任一条件建立不可绕过的人工待办：

- 规则涉及法律、财务、医疗、安全、合同承诺或其他高影响决定；
- 发现项严重度高，或 Agent 置信度低、无可定位证据、多个检查结论冲突；
- OCR/解析质量低、文档语言/格式不在已验证范围内；
- Agent、解析或策略服务发生降级、超时或重试后失败；
- 提交者对结论提出异议，或规则版本在运行中失效。

人工队列卡片应先展示规则、严重度、结论和证据，再提供完整上下文；不得只呈现模型的自然语言理由。审核者的可选动作应是：接受、改判、请求补充、标记解析问题、升级专家。每个动作需写入理由（尤其改判/接受高风险发现时）。

### 6.2 人工 → Agent：反馈闭环

人工决定可被聚合为评测集和阈值校准材料，但不应不经审核直接用于在线学习或修改生产规则。建议按规则、文档类型、语言、解析质量和审核者动作统计误报/漏报代理指标、人工覆盖率、处理时长与争议率；采用抽样复核以发现“自动通过”区域的系统性漏检。

来源事实：NIST AI RMF 的 `MEASURE` 与 `MANAGE` 功能强调对风险、影响和控制措施进行评估与管理；上述指标闭环是对该框架的工程化落实，而不是框架规定的唯一实现。

## 7. 可借鉴做法及来源

| 做法 | 来源事实 | 可用于本项目的设计建议 |
| --- | --- | --- |
| 先提取版式，再进行语义判断 | Azure Document Intelligence 提供内容、布局与结构化分析能力 | 审核 Agent 消费带页码/坐标的标准化表示，保留原件供人工比对 |
| 长文档采用异步处理 | AWS Textract 文档将异步分析作为处理多页文档的方式 | 创建任务即返回任务 ID，前端轮询/订阅状态，而非维持单个长请求 |
| 模型输出受约束并以证据为中心 | OpenAI Structured Outputs 文档说明可使模型输出匹配开发者提供的 JSON Schema | 使用服务端 schema 校验结果；schema 合格只代表格式合格，业务证据仍需校验和人工复核 |
| 安全隔离不可信内容与 Agent 权限 | OWASP 将 Prompt Injection、敏感信息泄露、过度代理权限列为风险 | 不向模型暴露广泛工具或凭证；文档文字不能改变系统规则或触发外部操作 |
| 将人类监督和风险度量纳入运行流程 | NIST AI RMF 提供治理、度量与管理的风险框架 | 建立基于影响等级的强制复核策略和审核质量仪表板 |

链接：

- [AWS Textract 异步分析 API](https://docs.aws.amazon.com/textract/latest/dg/async.html)
- [OpenAI Structured Outputs 指南](https://platform.openai.com/docs/guides/structured-outputs)

## 8. 对 DocAuditAgent 的初步建议与待验证项

1. 以“文档版本 + 审核运行 + 审核发现项”为核心对象，先实现明确状态机及只追加的审计事件，再扩展模型策略。
2. Agent 只产生候选审核意见，最终结果必须能追溯到规则版本与原文证据；默认将高影响或不确定事项交由人工。
3. 将解析质量作为路由信号而非隐藏实现细节：低质量输入应直接影响自动化范围与用户提示。
4. 在真实实施前，需要确认：目标文档类型/语言与大小上限、审核规则来源和版本治理、哪些场景允许自动放行、审核角色/权限、数据驻留与保留要求、可接受的处理时延和成本。
