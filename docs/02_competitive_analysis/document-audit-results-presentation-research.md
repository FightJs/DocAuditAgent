# 文档审核结果呈现调研

## 目标、问题与适用边界

本文调研面向合同、制度、报告等文档的自动审核结果页，回答四个问题：风险项应包含什么信息、审核人员怎样回到原文核验、哪些中间数据应当解释性呈现、人工如何处置并形成可追溯结论。

调研对象包括文档审阅、合规告警、代码安全告警和 AI 风险管理的公开资料。它们不是对具体产品功能的承诺；其中“来源事实”仅陈述引文所支持的能力或原则，“设计建议”则是为 DocAuditAgent 归纳的可迁移方案。扫描件 OCR、复杂表格、修订模式和多版本文档的定位精度，仍需在技术原型阶段验证。

## 审核结果模型

### 来源事实

- GitHub Code Scanning 将每条告警关联到规则、严重性、受影响的位置、状态与关闭原因；其告警页还可查看相关代码路径和修复建议。这说明高风险审阅工作流需要同时保留“结论、位置、依据、处置状态”。[1]
- Microsoft Purview DLP 告警支持按严重性查看与调查，并在告警详情中提供活动、匹配的敏感信息类型等调查上下文。[2]
- NIST AI RMF 将可追溯性、透明度和可解释性列为可信 AI 特征；其治理建议强调记录系统用途、限制、职责与风险管理活动。[3]

### 设计建议：风险项最小数据契约

每一条风险应是可独立审核、可重新定位、可被人工覆盖的记录，而不是只输出一段模型摘要。建议字段如下：

| 分组 | 建议字段 | 审核人员要回答的问题 |
| --- | --- | --- |
| 身份与分类 | `risk_id`、风险类型、规则/策略版本、文档版本 | 这是什么问题，使用了哪套判断标准？ |
| 判断 | 标题、结论摘要、严重度、置信度、优先级 | 是否需要先处理，系统有多确定？ |
| 影响 | 可能后果、受影响主体、金额/期限/义务等结构化对象 | 风险影响谁、影响有多大？ |
| 原文证据 | 文档锚点、摘录、命中片段、上下文、页/节信息 | 我能否在原文中复核？ |
| 解释 | 命中规则、理由链、适用条件、反证/不确定性 | 为什么被判定为风险？ |
| 人工处置 | 状态、负责人、决定、备注、时间、覆盖原因 | 谁做了什么决定，为什么？ |

`严重度`、`置信度`与`处置优先级`不应合并。前者表示若成立的潜在影响，置信度表示系统对命中的确定程度，优先级则应由两者、截止日期和业务范围共同决定。这样能避免“低置信度的高影响事项”在列表中被静默忽略。

## 风险分级与信息层级

### 来源事实

- GitHub 的 Code Scanning 把严重度与告警状态分开管理，并允许关闭时选择原因；这支持“风险判断”和“处理结论”应为不同维度。[1]
- Purview DLP 可按严重性筛选和调查告警，体现严重度在调查队列排序中的作用。[2]
- WCAG 2.2 要求颜色不能作为传递信息的唯一视觉方式；因此，仅以红黄绿区分风险会排除部分用户。[4]

### 设计建议

采用四档严重度：`严重 / 高 / 中 / 低`，且每档显示文字标签、图标和非颜色差异。默认列表按“严重度 × 业务紧急度 × 未处理状态”排序；同时提供按文档章节、风险类型、负责人和审核状态的筛选。

列表行以一眼可判的摘要为主：严重度、风险标题、原文短摘录、位置和状态。把长篇理由、完整规则与解析数据放入右侧详情或展开层，避免风险队列被技术数据淹没。对于同一条款触发的多条规则，应提供“风险簇”：既保留独立风险 ID，又展示共同原文范围和主风险，降低重复处理。

## 原文定位与上下文呈现

### 来源事实

- Adobe Acrobat 的注释体系可将批注附着在 PDF 中的选定文本、区域或页面，并允许在注释列表中查看和回复。这是“列表结果—原文锚点—协作讨论”闭环的成熟模式。[5]
- GitHub Code Scanning 的告警详情以文件与行号作为入口，并呈现受影响路径，说明定位信息需要既能直达证据，也能展示其周边关系。[1]

### 设计建议

1. 为每个命中同时存储稳定锚点与展示锚点。稳定锚点优先使用文档版本 ID、页/节、段落 ID、字符区间与命中文本哈希；展示锚点使用用户易读的“第 3 页 · 4.2 违约责任 · 第 2 段”。
2. 点击列表项时在阅读器中定位、滚动并高亮命中区；默认展示命中段前后各一至两段。仅高亮关键词容易失去法律/业务限定条件，上下文是人工判断的一部分。
3. 当原始锚点失效（重新解析、OCR 修订或文档更新）时，不应悄悄跳转到相似文本。界面应标明“定位需确认”，展示原始摘录和候选位置，并要求人工重新绑定。
4. PDF、DOCX 与扫描件分别显示定位质量：原生文本可到字符范围，结构化文档可到段落/单元格，OCR 结果至少需要页、图像区域和 OCR 置信度。不要在低质量 OCR 上承诺精确文字定位。

## 解释性证据与中间数据展示

### 来源事实

- NIST AI RMF 认为透明度与可解释性应让相关人员获得其角色所需的信息，且应考虑人类—AI 团队中的监督与纠错能力。[3]
- NIST 的 AI RMF Playbook 建议记录数据、模型、测试、部署环境和已知限制等信息，以支持风险的可追溯管理。[6]

### 设计建议

解释层应回答“依据是什么、结论如何得到、哪里不确定”，而非暴露完整推理过程。建议按受众分层：

| 层级 | 内容 | 主要读者 |
| --- | --- | --- |
| 审阅层（默认） | 风险理由摘要、命中摘录、适用规则、潜在影响、建议核查问题 | 业务/法务审核员 |
| 证据层（按需展开） | 规则条件与命中字段、结构化提取值、引用来源、模型/策略版本、置信度及其含义 | 高级审核员、管理员 |
| 诊断层（受控） | 文档解析状态、OCR 置信度、失败原因、重试时间、输入输出版本关系 | 运营、支持、研发 |

应显示可行动的不确定性，例如“付款期限已提取为 30 天，但扫描质量较低，请核对原文”，而非单独给出一个无解释的 0.62 分数。模型解释必须与证据区分：规则命中、原文引用和模型生成的风险说明分别标记；没有直接原文依据时，应明确标注为“待人工确认的推断”。

避免向普通审核员呈现逐 token、内部链式推理或无上下文的大量特征值：这些内容难以校验，也会造成虚假的确定感。可审计性依靠可复现的输入版本、策略版本、命中证据和人工决定，而不是暴露模型内部思考。

## 人工审核理解、判断与处置流程

### 来源事实

- GitHub 对告警提供已修复、已关闭等状态与关闭理由，表明处置不是简单删除结果，而应保存结果生命周期。[1]
- Acrobat 注释支持回复和协作，表明原文级讨论可作为审核决定的上下文，而不应散落于外部聊天记录。[5]
- NIST AI RMF 强调明确人类监督责任与可追溯的风险管理活动。[3]

### 设计建议：状态机与操作

建议风险生命周期为：`待审核 → 处理中 → 已确认 / 误报 / 需补充信息 / 已缓解 / 已接受风险`。其中“已确认”仅代表判断成立；“已缓解”应关联修改后的文档版本或整改证据；“已接受风险”必须填写授权人、理由和有效期。

审核详情页应提供以下操作：

- 确认、标记误报、要求补充、转交负责人、合并重复项、批量处理。
- 在原文锚点旁添加评论与引用，说明判定依据或需要作者修改的位置。
- 对自动结论执行覆盖时填写标准化原因，并保留原结论、覆盖人、时间与前后版本。
- 文档更新后重新审核：将旧风险标为“已过期/待比对”，以风险 ID 和证据绑定关系串联前后版本，不能把旧决定直接复制为新版本结论。

批量处理应被限制为同一风险类型、相近证据与同一处置理由的项目；对“严重”风险、低定位质量风险和接受风险操作，建议要求二次确认。这样既能处理大批量模板文档，也能防止一键关闭掩盖关键问题。

## 可借鉴做法与建议优先级

| 可借鉴模式 | 参考来源 | 对 DocAuditAgent 的落地建议 |
| --- | --- | --- |
| 告警的规则、位置、状态和关闭理由并列 | GitHub Code Scanning [1] | 将风险证据和处置记录建模为一等数据，支持回溯与统计。 |
| 严重性驱动调查队列，详情包含活动上下文 | Microsoft Purview DLP [2] | 结果页先服务于“下一步怎么做”，再展示技术细节。 |
| 原文锚定批注与线程讨论 | Adobe Acrobat [5] | 阅读器和风险侧栏双向联动；决定与讨论绑定到证据。 |
| 透明度、可解释性与人类监督 | NIST AI RMF [3][6] | 以角色分层解释、不确定性提示和可追溯版本记录实现可信审核。 |
| 非颜色唯一编码 | WCAG 2.2 [4] | 风险徽标使用文字、图标、形状与色彩组合，并保留筛选和键盘可达性。 |

建议 MVP 的优先顺序为：

1. 风险列表、严重度/状态分离、原文高亮和上下文摘录；
2. 单条风险的规则依据、文档/策略版本和确认/误报/转交留痕；
3. 解析/OCR 质量提示、风险聚类、跨版本比对和审批型“接受风险”。

## 风险、待验证问题与下一阶段交付物

待验证问题包括：不同解析器能否生成稳定段落锚点；扫描件中的坐标和 OCR 文本如何对齐；大文档中定位和高亮的性能；企业客户对“严重度”定义与审批链的差异；以及自动审核输出是否可在给定策略版本下复现。

下一阶段应以一份交互原型规格验证“列表—详情—原文—处置”四区域之间的跳转、空态、定位失败、误报申诉和文档版本变化场景，并将风险项数据契约与 API 设计对齐。
