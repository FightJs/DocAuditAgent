# DocAuditAgent 业务问题建模

## 1. 建模目标与产品定位

DocAuditAgent 是一个面向合同／法务文档审核的**证据化审核辅助与风险路由系统**。它把文档提交、材料校验、解析、规则比对、风险整理和人工决定组织为可追溯的业务流程。

产品不输出具有法律效力的意见，不自动批准合同例外，也不自动放行高风险签约。Agent 的职责是形成带原文证据和不确定性说明的候选审核结果；有权限的人员负责审核、修改、升级或批准最终决定。

## 2. 核心业务问题

### 2.1 需要解决的问题

| 业务问题 | 当前业务后果 | DocAuditAgent 的业务处理方式 |
| --- | --- | --- |
| 审核材料分散且质量不稳定 | 附件缺失、版本混淆、扫描件不可读会使审核结论失去基础 | 将材料完整性、可读性、版本和适用范围作为审核准入条件；不满足时转补件或人工处理 |
| 条款比对和风险定位依赖人工重复查找 | 首轮审阅慢、标准不一致、重要偏离项容易遗漏 | 基于已批准的模板、条款库和红线规则形成候选风险项，并关联原文位置与依据 |
| 风险结果缺少证据和上下文 | 审核人难以判断模型结论，结果无法复核 | 每个风险项保留原文定位、上下文、规则版本、理由、置信度和建议动作 |
| 自动化与专业判断之间缺少明确交接 | 低价值事项占用专家时间；高风险事项又可能被错误放行 | 依据风险等级、置信度、解析质量和红线规则进行分流，在必要节点强制人工复核 |
| 审核过程和最终决定不可追溯 | 规则变化、文档更新或争议发生时无法还原依据和责任 | 将文档版本、审核运行、风险项、人工决定和状态变更纳入同一案件记录 |

### 2.2 非目标

- 不替代法务、合规人员或签署授权人的判断。
- 不将“未发现风险”解释为“合同无风险”或“允许签署”。
- 不在 MVP 阶段覆盖所有合同类型、所有法域或自动化履约执行。

## 3. 目标用户与角色边界

| 角色 | 业务目标 | 主要动作 | 不能承担的动作 |
| --- | --- | --- | --- |
| 业务提交者 | 快速提交材料并获得可行动的审核反馈 | 创建审核案件、上传文件、补件、查看授权范围内的结果、重提 | 修改审核证据、查看无权限案件、作出法务审批 |
| 法务／合规审核者 | 在原文和依据支持下作出专业判断 | 复核风险、确认/改判/驳回、要求补充、升级专家、记录理由 | 无证据批量确认高风险结果、将模型建议当作自动法律意见 |
| 条款／策略负责人 | 维护审核基线与风险阈值 | 管理模板、条款库、红线规则、适用范围和版本 | 静默改写已完成案件的规则或结果 |
| 管理员／运营负责人 | 保证系统可控、可审计和持续改进 | 管理权限、队列、保留策略、质量指标和异常处置 | 代替专业审核者作出具体案件的法务判断 |

MVP 的主要服务对象是使用标准合同开展业务的提交者，以及负责首轮与高风险复核的法务／合规审核者；策略负责人和管理员是保障该流程运行的支撑角色。

## 4. MVP 业务场景

MVP 聚焦规则成熟、频率较高、边界清晰的合同类型，例如 NDA 或标准采购／服务协议。以下场景按同一案件链路组织，而非独立功能堆叠。

### 场景 A：材料准入与审核任务创建

**触发**：业务提交者发起合同审核并上传合同正文及相关附件。

**业务目标**：确认材料可被可信地审核，防止缺失、损坏、版本不明或不适用的文件进入自动审核。

**业务结果**：

- 材料完整且可读：创建审核案件和文档版本，进入解析与准备。
- 材料不足或质量异常：生成补件／人工处理待办，不输出推断性审核结论。

### 场景 B：基于审核基线的首轮风险识别

**触发**：文档已解析，且已根据合同类型、交易背景和适用范围匹配到可用的模板、条款库和红线规则。

**业务目标**：把“条款与基线是否偏离”转化为可复核的风险项，帮助审核者优先处理高影响事项。

**业务结果**：每项候选风险至少包含风险类别、严重度、置信度、原文定位、上下文摘录、关联依据、建议动作和当前处置状态。

### 场景 C：人工复核与风险处置

**触发**：存在红线条款、高严重度项、低置信度项、无可定位证据项、解析质量异常项、规则冲突项或提交者异议。

**业务目标**：由有权限的审核者在完整证据包基础上完成判断，而不是以模型摘要直接放行。

**业务结果**：审核者可确认风险、标记误报、要求补充、转交专家、记录改判原因或接受风险。所有决定与操作者、时间、理由、文档版本绑定。

### 场景 D：文档更新后的重审与交付

**触发**：提交者补件、修改合同、切换审核基线，或人工要求重新审核。

**业务目标**：让新版本获得新的审核结论，同时保留旧版本及其审核决定的可追溯性。

**业务结果**：新文档版本创建新的审核运行；旧运行保持只读，不允许覆盖或复用为新版本结论；最终交付只展示经授权、已完成处置的结果。

## 5. 自身业务主流程与规则逻辑

### 5.1 案件主流程

```text
创建案件
→ 上传与准入
→ 解析与标准化
→ 选择审核基线
→ Agent 形成候选风险
→ 风险聚合与分流
→ 人工复核或补件
→ 最终交付
→ 归档与质量反馈
```

### 5.2 业务状态

审核案件在业务上至少需要表达以下状态：

`created`、`uploading`、`accepted`、`rejected`、`parsing`、`parse_failed`、`ready`、`agent_reviewing`、`agent_completed`、`agent_failed`、`triaged`、`human_reviewing`、`approved`、`changes_requested`、`rejected`、`delivered`、`resubmitted`、`archived`。

其中 `parse_failed`、`agent_failed` 和材料被拒绝都不能被解释为“审核通过”；`approved` 必须由具备相应权限的人工审核者作出，除非业务另行定义并记录低风险自动放行规则。

### 5.3 分流与处置规则

1. **准入规则**：文件格式、可读性、附件、版本和适用范围不满足要求时，不进入 Agent 审核。
2. **基线规则**：每次审核运行只能使用明确版本和适用范围的模板、条款库、红线规则及外部依据。
3. **证据规则**：没有原文定位或适用依据的候选结论必须标记为待人工确认，不能作为自动放行依据。
4. **升级规则**：红线、高严重度、低置信度、解析质量低、结论冲突、规则失效或提交者异议，必须进入人工队列。
5. **版本规则**：原文或审核基线变化后必须创建新的文档版本或审核运行；历史结果只读保存。
6. **决定规则**：确认、误报、补件、转交、风险接受等人工动作必须记录责任人、理由和发生时间。

## 6. 从功能清单到业务数据模型

功能清单关注“上传、解析、审核、展示、人工处理”等动作；业务建模需要把这些动作收敛为可持续流转、可追溯和可度量的对象。

| 业务对象 | 业务含义 | 关键关系 |
| --- | --- | --- |
| 审核案件 | 一次业务审核请求及其整体生命周期 | 包含一个或多个文档版本和审核运行 |
| 文档版本 | 某次提交的合同正文、附件及其版本身份 | 属于一个案件；被解析并参与一个或多个审核运行 |
| 解析结果 | 可供审核和人工定位的标准化文本、结构和质量信号 | 对应一个文档版本；为风险证据提供锚点 |
| 审核基线 | 模板、条款库、红线规则和适用范围的版本化组合 | 被审核运行引用；决定风险判断边界 |
| 审核运行 | 使用特定文档版本和审核基线产生候选结果的一次执行 | 属于案件；产出风险项和运行状态 |
| 风险项 | 可独立审核和处置的候选问题 | 属于审核运行；关联证据、规则、严重度和处置状态 |
| 证据 | 支持风险结论的原文位置、上下文和关联依据 | 关联风险项、文档版本和审核基线 |
| 人工决定 | 对风险项或案件作出的确认、改判、补件、转交或接受风险动作 | 关联风险项/案件、操作者、理由和时间 |
| 审计事件 | 对关键状态、规则选择和人工动作的不可变记录 | 关联案件、文档版本、运行或决定 |

该对象集合是后续数据模型和 API 设计的业务语义来源；本阶段不定义具体表、字段类型、接口或存储方案。

## 7. 后续设计阶段的输入

| 后续阶段 | 应继承的业务输入 |
| --- | --- |
| 核心交互链路设计 | 案件状态、补件/重提、人工复核、原文定位与结果交付流程 |
| 产品原型规范 | 风险队列、详情证据包、阅读器定位、人工处置和状态提示 |
| 系统架构设计 | 上传/解析/审核/人工复核/审计的职责边界及状态编排要求 |
| 数据模型设计 | 审核案件、文档版本、审核基线、审核运行、风险项、证据、决定和审计事件 |
| API 规范 | 案件、上传、运行、风险项、人工决定、状态查询与版本关系的业务契约 |

## 8. 本阶段收口

业务建模已将既有功能清单收敛为“以审核案件为中心、以文档版本和审核基线为输入、以风险项和证据为中间结果、以人工决定为最终控制点、以审计事件保证可追溯”的业务系统。

在进入系统架构、原型或数据模型设计前，应以本文件的角色边界、MVP 场景、状态规则和业务对象为统一输入；任何扩展合同类型、法域、自动放行范围或外部集成的需求，都应先更新 Plan 和业务规则。
